### 1.3 全局开发约束（违反会导致编译失败或线上事故）

1. **数据库变更走 EF 迁移**（前置任务 P0 完成后生效）。新增表/列一律
   `dotnet ef migrations add <Name>`，启动时由 `Migrate()` 应用；**不要再往 `Program.cs` 里加手写 DDL**。
   客户端本地 SQLite（`sqlite-net-pcl`）不受此约束，仍用建表语句（见 V2.6/V2.7）。
   ⚠️ 在 P0 落地之前开工的版本才需要沿用老的幂等 SQL 写法，但 P0 是 V2.3 的前置，实际不会遇到。
2. **包版本集中管理**。`Directory.Packages.props` + `CentralPackageTransitivePinningEnabled`，
   新增 NuGet 包只写 `<PackageReference Include="X" />`，版本登记到 props；设计时包加 `PrivateAssets="all"`。
3. **搜索一律 `EF.Functions.ILike(col, LikePattern.Contains(kw))`**，不要用 `Contains`（PostgreSQL 的 LIKE 区分大小写）。
4. **平台条件编译对称**：`#if WINDOWS` / `#elif ANDROID` 成对处理，改一端必须确认另一端。
   快速验证：Windows 目标约 9s，Android 目标约 3m40s。
5. **弹层一律 `SongMenuHelper.AttachOverlay(page, overlay)`**，绝不替换 `page.Content`
   （MAUI 10.0.60+ Windows 会崩 `COMException 0x800F1000`）。
6. **`HttpClient` 不设 `BaseAddress`**，所有请求走 `ApiConfig.Absolute(url)`，保证改地址后下一次请求即生效。
7. **原生事件订阅不会随页面离开解除**（`PointerPressed` 等）：回调里先取局部变量判空再操作，
   并在 `OnNavigatedTo` 把状态装回来（V2.6 涉及本地播放页时同样适用）。
8. **后台接口必须带 `[Authorize(Roles = "admin")]`**，角色来自 JWT 的 `ClaimTypes.Role`。
9. **改完服务端必须重建并重启 API**；重建前先停 API，否则 DLL 占用报 MSB3027/MSB3021 假错。
10. **播放入口必须带整张列表**（`PlayerService.NextAsync` 在队列长度为 1 时下一首等于自己）。

## 3. 各版本设计

## P0 EF Core 迁移基建（V2.3 前置优先任务）

> 状态：**已完成**。自 V2.3 起库结构变更一律走 `dotnet ef migrations`，启动时 `Migrate()` 应用，见下方 P0 节。

### 3.P0.1 背景

项目从 V0.1 起就没用过 EF 迁移：启动时 `EnsureCreated`（只在库不存在时建表），
再执行 6 段手写幂等 DDL 补列补表（`Songs.CoverUrl`、`ArtistFollows` 表、`Playlists.IsSystem` + 回填、
`Users.Role`、`Users.IsDisabled`、`Categories` 三列 + 种子）。这套做法在"只加可空列"时还能凑合，
但随着 V2.5 起连续 6 个版本都要动表结构，它会暴露三个硬伤：

1. **表达能力不足**：列改名、类型调整、外键与索引变更，手写 `ADD COLUMN IF NOT EXISTS` 表达不了，只能继续糊补丁。
2. **不能回滚**：出错只能手工改库，没有版本化的回退点。
3. **环境漂移**：补丁 SQL 是否执行过取决于历史启动时机，开发 / Docker / Windows 安装包三个形态的库结构容易不一致。

所以把它定为 V2.3 的前置优先任务：**先把变更管理方式换成迁移，再开始做功能**。

### 3.P0.2 设计方式

**目标形态**：结构变更一律 `dotnet ef migrations add <Name>`，启动时统一 `Migrate()`；
`Program.cs` 里那段手写 DDL 在过渡完成后删除。

**难点**：现有库都是 `EnsureCreated` 建的，没有 `__EFMigrationsHistory` 表，
直接 `Migrate()` 会因为"表已存在"而失败。

**过渡方案：三态识别 + 一次性基线缝合**

| 状态 | 判据 | 动作 |
|---|---|---|
| 全新库 | 核心表（如 `"Songs"`）不存在 | 直接 `Migrate()` 建库 |
| 老库未基线 | `"Songs"` 存在且 `__EFMigrationsHistory` 不存在 | ① 先跑现有幂等 SQL 对齐结构 → ② 建历史表并插入 `InitialCreate` 记录 → ③ 再 `Migrate()`（此时应无待应用） |
| 已基线 | 历史表存在 | 直接 `Migrate()` |

**种子数据不进迁移**：`Categories` 的 5 条种子（`ON CONFLICT DO NOTHING`）继续留在启动流程里，
**不要**改成 `HasData`。线上分类可能已被人工改名，`HasData` 会带来覆盖/删除语义，风险大于收益。

**过渡完成后的清理**：确认所有环境历史表都已存在之后，删除"基线缝合"分支与手写 DDL 段。
建议放在 P0 上线后的下一个版本再删——不要和首次上线同一版删，留一个观察窗口。

### 3.P0.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 迁移工具 | `dotnet-ef` **本地工具**（`.config/dotnet-tools.json` 入库） | 团队与 CI 版本一致；全局工具容易版本漂移 |
| 迁移程序集 | `YinYanMusic.Data`（`--project`），启动项目 `YinYanMusic.Api`（`--startup-project`） | DbContext 在 Data 工程，连接串取自 Api 配置 |
| 基线策略 | 代码内一次性自动缝合 | 不依赖每台机器手工插历史记录，避免遗漏某个环境 |
| 种子数据 | 保留启动 SQL，不进 `HasData` | 与线上已有分类数据共存，避免覆盖 |
| 生产执行 | 启动自动 `Migrate()` | 单机/单容器部署，规模可控；**升级前必须备份库** |

### 3.P0.4 开发思路

1. `dotnet new tool-manifest`（若无）→ `dotnet tool install dotnet-ef`（版本与 EF Core 10.0.4 对齐）。
2. 生成初始迁移：
   `dotnet ef migrations add InitialCreate --project src/YinYanMusic.Data --startup-project src/YinYanMusic.Api`
3. 人工核对 `InitialCreate`：确认覆盖全部实体表、外键、索引，并与现有库结构一致
   （重点核 `ArtistFollows`、`IsSystem`、`Role`、`IsDisabled`、`CoverUrl`、Categories 三列）。
4. 改 `Program.cs`：三态识别 + 基线缝合 + `Migrate()`；保留 `DROP_DB=1` 与种子 INSERT，
   在缝合分支上标注"过渡完成后删除"。
5. 同步改 `Scanner/Program.cs` 第 100 行附近的提示文案（那里仍写着"让 EnsureCreated 按当前模型建表"）。
6. 各环境验证（见测试用例），确认 `GetPendingMigrations()` 为空。
7. Dockerfile 与 CI 无需改动（启动即迁移）；Windows 安装包形态同样在进程启动时迁移。

## P1 API 文档（OpenAPI + Scalar UI，V2.3 前置任务）

> 状态：**已完成**。`/openapi/v1.json` 与 Scalar UI 均已就位（`Program.cs` 的 `MapOpenApi` / `MapScalarApiReference`）；生产环境默认关闭，由 `OpenApi:Enabled` 开关控制。

### 3.P1.1 背景

现在的 `Program.cs` 里 `app.MapOpenApi()` 被包在 `if (app.Environment.IsDevelopment())` 中，
而 Docker 与 Windows 服务形态都是 `ASPNETCORE_ENVIRONMENT=Production`，于是部署之后：

- `/openapi/v1.json` 直接 404；
- 更没有任何可视化文档页面 —— 现场排查接口只能翻代码或抓包。

这里有个容易误解的点：**`Microsoft.AspNetCore.OpenApi` 只负责生成 OpenAPI 文档（JSON），不提供 UI**。
.NET 9 起官方模板已不再内置 Swashbuckle，所以"调了 MapOpenApi 却看不到 Swagger 页面"是预期行为，UI 要另外接。

连带影响还有一处：后台前端 `web/admin` 的 `npm run gen:api` 抓的正是
`http://localhost:5116/openapi/v1.json`，部署形态下同样拿不到，契约重新生成会失败。

### 3.P1.2 设计方式

- 引入 **Scalar**：`app.MapScalarApiReference()`，UI 落在 `/scalar/v1`。
  ⚠️ `MapOpenApi()`（出 JSON）与 `MapScalarApiReference()`（出 UI）**必须成对出现**，只调后者会得到 404。
- **文档不再绑死 Development**：改用配置开关 `OpenApi:Enabled` 控制，默认 Development 开、Production 关，
  需要时按环境打开。
- **访问控制不在代码里造轮子**：API 绑 `0.0.0.0` 且 CORS 全开，把完整接口清单暴露到公网不合适。
  生产若要开放文档，由 **Nginx 侧限制**（内网 IP 白名单或 Basic Auth）。
- **Bearer 调试**：加一个 `BearerSecuritySchemeTransformer`（`IOpenApiDocumentTransformer`）把 Bearer
  安全方案写进文档，UI 上就能直接填 token 调 admin 接口 —— 后台联调（V2.3）会反复用到。
- **保持 `/openapi/v1.json` 路径不变**（`gen:api` 依赖它），并保留现有的文档标题/版本/描述 transformer。

### 3.P1.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| UI | **Scalar.AspNetCore**（2.11.x） | .NET 9/10 起官方模板已不含 Swashbuckle；Scalar 与 `Microsoft.AspNetCore.OpenApi` 天然配套，一行接入，支持 OpenAPI 3.1 与代码示例 |
| 备选 | Swashbuckle.AspNetCore.SwaggerUI | 生态老、插件多；但它自带 SwaggerGen，与已接入的内置 OpenApi 生成重复，迁移收益低 |
| 访问控制 | Nginx 限制（IP 白名单 / Basic Auth） | 不改代码、不动鉴权体系；生产默认不暴露 |
| 生产开关 | `OpenApi:Enabled` 配置项 | 默认关闭，按环境显式打开 |

### 3.P1.4 开发思路

1. `Directory.Packages.props` 登记 `Scalar.AspNetCore` 版本；Api 工程加 `<PackageReference Include="Scalar.AspNetCore" />`。
2. `Program.cs`：`MapOpenApi()` 移出 `IsDevelopment()`，改为按 `OpenApi:Enabled` 判断；
   紧接着 `MapScalarApiReference(...)`（标题"音言音乐 API"、深色主题、默认 HttpClient 用 C#/HttpClient）。
3. 新增 `BearerSecuritySchemeTransformer`，注册进 `AddOpenApi(options => options.AddDocumentTransformer<...>)`。
4. `appsettings.json` 增 `"OpenApi": { "Enabled": false }`，开发环境置 true；
   Docker/安装包形态用环境变量 `OpenApi__Enabled=true` 按需打开。
5. Nginx：生产若开放，对 `/openapi` 与 `/scalar` 加 IP 白名单或 Basic Auth，**不要裸奔**。
6. 验证：见测试用例；重点是"开发能看、生产默认关、打开后能带 token 调 admin 接口"。

### 3.3.6 上线后修复记录（2026-09-23）

**表单里"选完值不显示"——`useCrudTable` 的 shallowRef 草稿（两个独立缺陷叠加，用户报的是第 2 个）**

现象：后台「编辑歌曲」对话框里的**分类**下拉，选完值框里仍显示占位符；重新打开也看不到已保存的分类。

1. **读路径缺字段（后端）**：`Core/Dtos/MusicDtos.cs` 的 `SongDto` **没有 `CategoryId`/`CategoryName`**，`SongService` 的列表投影与 `SongGetAsync` 的 `ToDto` 都没带这两列 —— 而写入路径（`CreateAsync`/`UpdateAsync` 的 `categoryId`/`clearCategory`）是好的，前端 `catalog.ts` 也早就声明了这两个字段。于是"存得进去、读不回来"，下拉永远显示占位符。
   修复：补齐 DTO 两个字段 + 列表投影 + `MappingExtensions.ToDto`，并在 `GetAsync`/`CreateAsync`/`UpdateAsync` 补 `Category` 导航的加载（让 POST/PUT 的响应也带上分类名）。
2. **前端草稿不是深响应（后台前端）**：`useCrudTable` 用 `shallowRef<T>` 存编辑草稿，而表单里 `v-model="table.editing.xxx"` 改的是**对象属性** —— shallowRef 不追踪属性写入 → 父组件不重渲染 → 子组件拿到的 props 一直是旧值 → `el-select` 选完值框里还是旧值、`el-input-number` 点 + 号数字不动、`el-color-picker`/`IconPicker` 同理。**值其实已经改了，保存也生效**（实测：选「日语专区」保存后库里确实写成 14），只是界面不刷新，最容易被当成"根本没选中"。原实现只对 IconPicker 用 `syncEditing` 打了点状补丁（composable 注释里记录了这件事），其余字段都没管。
   修复：`openDialog` 里把草稿包一层 `reactive()`（外层仍是 shallowRef，替换引用的语义不变），`syncEditing` 改成直接写属性 —— 注意**不能**再写成 `editing.value = { ...cur, [key]: value }`，展开会把 reactive 代理摊回普通对象、响应性随之丢失。这是根因修复，`Songs`/`Albums`/`Categories` 三个页面的同类字段一起好了（`Artists` 只有原生 input，本来就不受影响）。

实测（浏览器真实交互）：分类 `可选 → 华语专区`、歌手 `Ado → Aimer`（Songs）、所属歌手 `(K)NoW_NAME → Ado`（Albums）、时长 `259 → 261`（el-input-number）、图标预览 `music_note → audiotrack`（IconPicker，走 `syncEditing`）；保存后重开对话框能正确回显。验收用的测试数据（给《向日葵》临时设置的分类）已还原为原值。

**可空外键的「清空」语义：从「清空」勾选框改成下拉自带的 ×**

分类旁边原来有个「清空」勾选框（勾上时下拉被禁用）。它存在的唯一理由是后端 `UpdateSongRequest` 是**局部更新**语义 —— `categoryId: null` 在那层只表示"这次不改"（见 `SongService.UpdateAsync` 的 `else if (req.CategoryId is int cid)`），所以清空必须靠 `clearCategory: true` 显式表达。

问题是分类下拉本身就是 `clearable` 的，用户更自然的操作是点 ×。**实测**：点 × 后框里显示「可选」、保存返回 200，但库里分类纹丝不动（后端把 null 当"不改"），重新打开又冒出来 —— 界面上没有任何提示。专辑更彻底：下拉也是 `clearable`，却连清空勾选框都没有，所以**专辑从界面上根本清不掉**。

修复：
- 前端 `Songs.vue` 去掉勾选框与相关状态，改由"字段为空即清空"推导 `clearCategory` / `clearAlbum`（表单整份提交，空即清空，语义无歧义）；点 × 从此真正生效。
- 后端给 `UpdateSongRequest` 补 `ClearAlbum`，与 `ClearCategory` 对齐（`UpdateAsync` 里 clear 判断优先于赋值，与分区那段写法一致）。

实测：① 打开对话框原样保存 → `albumId=757 / categoryId=10` 都保留（不误清）；② 点分类 × 保存 → 库里 `categoryId=null`；③ 点专辑 × 保存 → 库里 `albumId=null`（此前不可能做到）。测试数据已还原。

> 排查插曲：把注释写进模板属性里的内联箭头函数时，注释中含**直引号**（`"这次不改"`）会提前截断该属性，`vue-tsc` 报的是误导性的 `TS1005 '}' expected`（指向 `</script>`）。模板表达式里要引号一律用「」。

**列表页搜索框点 × 不刷新**

现象：全部列表页（歌曲 / 专辑 / 歌手 / 分区 / 歌单 / 用户）的搜索框点 × 只清空了输入框，列表仍停在上一轮的筛选结果，得再按一次回车才恢复。

原因：搜索是**显式提交**式的 —— `@keyup.enter="onSearch"`（重置回第 1 页再请求），而 `clearable` 的 × 只是把 `keyword` 置空，本身不触发任何查询，两者没连起来。

修复：6 个搜索框统一补 `@clear="onSearch"`（用 `useCrudTable` 的 4 个页面是 `table.onSearch`）。点 × 从此等价于「清空 + 立即查询」。

实测：歌曲页输入「向日葵」→ 1 行，点 × → 恢复整页 20 行；用户页输入「admin」→ 1 行，点 × → 恢复全部 8 行。

> 排查插曲：早先有一次"输入关键词回车后列表没变"，后来确认是**测试脚本**的问题 —— Playwright 的 `fill()` 直接赋值、没触发 Vue 的输入事件，改用真实按键 `type()` 后搜索一直正常。搜索功能本身没有问题，别照着这个假象去改代码。

**列表页搜索统一为「多字段匹配」，并修掉转义静默失效的既有缺陷**

**(1) 多字段匹配（与歌曲页对齐：一个关键词命中多个字段）**

歌曲页一直是 `标题 / 歌手 / 专辑` 三选一命中，其余页只匹配自己的名字，用起来不一致（搜歌手名在歌曲页有结果、在专辑页却空空如也）。现已对齐：

| 页面 | 现在匹配 | 变更 |
|---|---|---|
| 专辑 | 专辑名 / **歌手名** | 新增歌手名 |
| 歌手 | 名字 / **地区** / **类型** | 新增地区、类型 |
| 歌单 | 歌单名 / **创建者名** | 新增创建者 |
| 分区 | 名称 / **宣传语** | 新增宣传语；仍是客户端过滤（分区只有个位数），但把比较改成**大小写不敏感** —— 原来用 `includes`，搜 `k-pop` 命中不了「K-Pop专区」，与服务端的 ILIKE 语义分叉 |
| 用户 | 用户名 / 昵称 | 本来就对，未动 |

歌单的创建者取 `Owner.DisplayName`，与列表展示的 `OwnerName` 同一个值（搜到的和看到的对得上）。4 个搜索框的占位符同步改成能体现可搜字段（占位符是用户唯一的提示，如"搜索专辑 / 歌手"）。

**(2) `LikePattern` 的转义在 PostgreSQL 上静默失效（既有缺陷，波及全项目所有搜索）**

`LikePattern.Contains` 会把 `_` / `%` / `\` 转义成 `\_` / `\%`，但 **Npgsql 生成的 SQL 是 `ILIKE @p ESCAPE ''`** —— 空转义符等于**禁用转义**，反斜杠退化成字面字符，于是**关键词里只要含 `_` 就永远匹配不到任何东西**（`%`、`\` 同理，只是平时不易察觉）。

实测（按创建者搜歌单）：`yeun` 命中 2 条，而完整用户名 `ck_yeun9` 命中 **0** 条；单独搜 `_` 也是 0 —— 库里明明有下划线。用户名、歌单名里带下划线很常见，所以这条影响面不小。

修复：`LikePattern` 增加 `EscapeChar` 常量（`\`，附成因说明），全部 **17 处** `ILike` 调用改为显式传转义符
`EF.Functions.ILike(col, pattern, LikePattern.EscapeChar)`。漏传就退回旧行为，所以注释里写清了"必须显式传"。

**专辑封面 / 歌手头像支持存 base64（2026-09-23）**

**专辑：按发行时间排序 + 行内显示发行时间与曲目数（2026-09-23）**

接上一条继续做专辑列表：

**① 曲目数（新字段）**：`AlbumDto` 补 `int TrackCount = 0`，列表接口在投影里用相关子查询算 `db.Songs.Count(s => s.AlbumId == a.Id)`（与 `ArtistDto` 的 songCount/albumCount 同一套做法，不加冗余列）。`MappingExtensions.ToDto` 的 `trackCount` 做成参数、由调用方查好传入 —— 映射器里不查库，避免藏一个 N+1；创建/更新响应照实传 0（那一刻确实还没歌）。

**② 排序**：`GetAlbumsAsync` 从 `OrderBy(Id)` 改成**发行时间倒序**：
```csharp
.OrderBy(a => a.ReleaseDate == null)     // ⚠️ PostgreSQL 的 DESC 默认把 NULL 排最前，必须先按"有没有日期"排一次
.ThenByDescending(a => a.ReleaseDate)
.ThenByDescending(a => a.Id)             // 同一天的多张按 Id 稳定排序
```
这条对有发行日期的专辑是"最新在前"，没日期的沉到最后。实测 Ado：`2024-01-01 → 2023-01-01 ×2 → 2022-01-01 → 无日期 ×3`。

**联合创作：一首歌挂多个歌手（2026-09-23）**

需求原话："如果存在一首歌并且 ATL 解析出多个歌手的情况下，我希望是做一个歌手分隔，同时这些歌手共有同一首歌，类似于联合创作那种。"

**模型：新增关联表，但保留 `Song.ArtistId` 作为"主歌手"**

```sql
CREATE TABLE "SongArtists" ("SongId", "ArtistId", "Position")   -- 复合主键，Position = 0 是主歌手
```
保留 `Song.ArtistId` 是**刻意的**：列表显示、专辑归属、播放页等仍以主歌手为准，所以既有代码与前台显示零回归；"归属"这一层才走关联表。迁移 `AddSongArtists` 建表 + **回填**（每首现有歌挂上它的主歌手），实测 81 首 → 81 条关联、0 首无归属。

**拆分规则（`AudioTagReader.SplitArtists`）**

| 规则 | 依据 |
|---|---|
| 分隔符只认 `;` 与中文顿号 `、` | ATL 把多值归一成 `;`（实测 `"Aimer;EGOIST"`）；中文标签里实测出现 `"陈小春、陈国坤、李灿琛…"` |
| **不**按 `/` 拆 | 乐队名里带斜杠很常见（`AC/DC`），一拆就成两个歌手 |
| `AlbumArtist` 只在主歌手字段为空时兜底 | 实测反例：某文件 `Artist="Aimer;EGOIST"`、`AlbumArtist="Aimer/EGOIST"`，两个都取会多出一个叫 `"Aimer/EGOIST"` 的**假歌手**（这一条是实现完导入后实测才发现的） |
| 去重（忽略大小写）、去空、最多 10 位 | 防脏标签造出几十个歌手 |

**写入路径**（都维护关联表）：
- 扫描 / 后台导入（`DirectoryScanService`）：新建歌曲时按标签里的顺序挂**全部**歌手（主歌手 Position = 0）

**读路径**（按歌手的一切查询都走关联表）：

| 位置 | 说明 |
|---|---|
| `SongService.GetPagedAsync(artistId)` | 联合创作的歌在**每位**歌手名下都能查到（歌手详情页的列表就是它）。仍保留 `ArtistId == artistId` 兜底 |
| 关键词搜索（全局 + 歌单内） | 命中任一关联歌手名 —— 搜 `EGOIST` 能找到《ninelie》 |

1. **扫描自愈**：库里已有歌若**主歌手名里含分隔符**（早期导入把多个人塞进一行的产物，如 `"陈小春、陈国坤、…"`）→ 扫描时自动拆开、重新挂载、修正主歌手，并把那个合并名歌手在无歌无专辑无人关注时**删掉**（它从来不是真歌手，留着会在歌手列表/搜索里抢位）。

**显示收口：全部歌手在 App 里只有一处定义（2026-09-23）**

需求原话："现在好多地方只显示主歌手 —— 迷你播放条、搜索页、歌曲列表、封面另存的文件名；超长就自动截断或者跑马灯。"

前面两条把**播放页**补齐了，但除播放页以外的每一处歌手文案仍是 `ArtistName`（只有主歌手）：首页热门、分区、搜索（热门 + 结果两处）、歌单详情、歌手详情、缓存管理、迷你播放条、三处队列浮窗（主页 / 播放页 / 本地音乐页）、以及封面另存的文件名。同一个联合创作歌手，在播放页是 `Aimer / EGOIST`、滑到列表里就只剩 `Aimer`。

**关键决定：拼一行的活儿收进 `SongDto.ArtistsDisplay`，而不是每个页面各挂一个转换器**

| 方案 | 为什么不选 / 为什么选 |
|---|---|
| 每个列表模板挂 `Artists` + join 转换器 | 分隔符会散落在转换器、`PlayerService`、队列构造三处各写一遍；而且**本地歌没有 `Artists`**（`null`），转换器看不到 `ArtistName`，得为它单开一条分支（或上 MultiBinding 双字段绑定） |
| **`SongDto.ArtistsDisplay`（计算属性 + `[JsonIgnore]`）** | 分隔符只有这一处定义；没有列表时自动退回主歌手，本地歌/老缓存行不用特判；XAML 直接 `{Binding ArtistsDisplay}`，C# 侧（队列、文件名）也取同一个属性 |

`[JsonIgnore]` 是刻意的：**拼成一行是客户端的观感决定，不该固化进接口契约** —— 线上传的仍然是有序列表 `Artists`，接口响应里不会多出 `artistsDisplay` 字段（后台 / 第三方要自己排版就自己 join）。

**播放页：点歌手名要能选人，关注按钮也要按人算（2026-09-23）**

需求原话："播放页点击歌手名的时候是跳转到歌手详情页的，现在如果有多个歌手，好像没法做到让用户选择要跳转到哪个歌手详情页。还有右侧的关注按钮也没做调整。"

**先查清了根因**：问题不在界面，在数据 —— 接口只给名字，没给 ID。

| 现状 | 后果 |
|---|---|
| 服务端三处投影都是 `Select(sa => sa.Artist.Name)`（`MappingExtensions` / `SongService` 列表 / `SongService` 喜欢列表） | 客户端拿到的是一串字符串，**没有任何 ID** |
| 跳转只能 `GoToAsync($"artist?artistId={song.ArtistId}")`（主歌手） | 想跳合作歌手，手上没有他的 ID |
| 关注按钮硬编码 `Player.Current.ArtistId` | 它连"这首歌还有别人"都不知道，更没法判断"那一位关注了没" |
| 界面只能靠名字反查歌手 ID | 同名歌手会认错人（库里真出现过合并出来的假歌手），不可取 |

**决定：`SongDto.Artists` 从名字数组升级为带 ID 的歌手数组**

```csharp
public record SongArtistRef(long Id, string Name);   // 第一位仍是主歌手
public IReadOnlyList<SongArtistRef>? Artists { get; init; }
```

一份数据同时够显示、跳转、关注 —— 不再"名字一处、ID 另一处"。显示侧零改动：`ArtistsDisplay` 照旧拼名字（那 9 处 XAML 绑定一行没动）。

**顺带修掉一个会静默退化的坑（比功能本身更值得记）**

歌单详情 / 歌单内搜索 / 歌曲详情走的是**内存映射** `song.ToDto()`，而这三处**没有 Include 关联表** → `SongArtists.Count == 0` → `ToDto` 的兜底分支生效 → 只返回主歌手。于是：

- `GET /api/songs?keyword=ninelie` → `artists` 两位 ✅
- `GET /api/songs/1626`（详情）→ 只给 `Aimer` ✗

**列表接口给两位、详情接口给一位** —— 这种不一致不会报错、只会让功能"在某些入口下莫名不灵"，是最难查的那类 bug。修法是补 Include（`SongService.GetAsync`、`PlaylistService.GetAsync`、`PlaylistService.SearchSongsAsync` 各一行），不是在前端兜底。

**交互（两条都按需求确认过）**

**菜单里的歌手项与关注项；播放页右侧两个按钮太挤（2026-09-23，用户看着截图提的）**

**一、右侧两个按钮挤在一起（布局）**

歌手那一行是 `[跑马灯][关注按钮]`，右边还并着**收藏按钮那一列**。原因不是"歌手名太长"本身，而是跑马灯的可用宽度算少了：

| 项 | 值 |

|---|---|---|
| `歌手：X` | 直接跳主歌手主页 | 单歌手照旧直接跳；**联合创作**文案变 `歌手：陈小春 等 9 人`，点开是「选择歌手」列表 |
| `关注歌手` / `取消关注歌手` | 只关注主歌手，状态也只看主歌手 | 单歌手照旧一键切换；**联合创作**是 `关注歌手...`（省略号＝展开一层，与「添加到歌单...」同一约定），点开是「关注歌手」列表：首行全部关注/全部取消，其余每位一行带 ✓ / + |

**顺手把重复实现收成一处**：`SongArtistSheets`（`Followable` / `PickArtistAsync` / `FollowAsync`）—— 播放页的歌手行与关注按钮、歌曲菜单的那两项都走它。之前我把这套逻辑写在播放页 VM 里，菜单再抄一遍必然两边行为不一致（这次就是漏了菜单那一处）。播放页只取"结果里哪位关注上了"更新图标（它不弹提示，图标就是反馈），菜单取同一结果里的文案弹提示。

**顺带修掉一个会挡住操作的隐患**：底部选择列表（`ShowBottomSheetAsync`）原本没有高度上限，行数一多就整个顶出屏幕上方 —— 联合创作最多 10 位歌手，「关注歌手」列表 = 表头 + 10 行 + 取消 = 12 行，最上面的「全部关注」会点不到。现在按**行数 × 行高（48dp）**估算内容高度：放得下就照旧用普通布局（面板自然贴着内容），超过屏高 80% 才套一个固定高度的 `ScrollView` 滚动。这是共用弹层，其余用到它的地方（歌曲菜单、歌单选择、音质选择）行为不变，只是多了一个"太长就滚"的兜底。

> **真机踩点（2026-09-23，用户报"弹出菜单样式有问题"）**：第一版写的是给 `ScrollView` 加 `MaximumHeightRequest = 屏高 × 0.7`。Android 上这是错的 ——
> `ScrollView` 会**撑满给它的可用高度**（内容默认 `VerticalOptions=Fill` 也一样被拉伸），于是连三行的「选择歌手」都变成了屏高 70% 的大白板，菜单下面一大片空白（用户截图里就是）。
> 改成"按 `layout.Height` 收口"同样无效：layout 自己也被拉伸，读出来的 `Height` 就是那个上限值。
> 结论：**在这个弹层里不要依赖 `ScrollView` 自己量高度**，判据只能用与布局无关的"行数 × 行高"。上限也顺势从 70% 提到 80%，让 10 位歌手那种上限场景（12 行 ≈ 630dp）在 800dp 高的屏幕上整屏放得下、连「取消」都不用滚。
> 同一次真机验证：`选择歌手`（2 行）贴合内容、歌曲菜单（8 行）贴合内容、9 位歌手的 `关注歌手`（11 行）全部可见且不裁切。

**歌手详情页歌曲列表：先量再改，懒加载 + 并行 + 播放前补齐（2026-09-23）**

需求原话："歌手详情页里的歌曲列表加载好像有点慢，体验感不太好，能不能改成懒加载之类的提升体验感？"

**先量清楚"慢"在哪**（否则容易去优化不痛的地方）：

| 场景 | 改前 |
|---|---|
| 服务端冷启动后**第一个**请求：36 首的歌手页（`pageSize=100`） | **0.691s** |
| 暖机后同一个请求 | 0.015s |

差异全在服务端进程刚起来的时候：`FillDurationsAsync` 会对**每首还没进过进程内缓存**的歌都读一遍音频文件取时长（36 首 ≈ 0.6s），而那个进程内缓存只在进程生命周期内有效 —— 于是"快慢取决于服务端刚不刚重启"，是体验上最难解释的那种慢。客户端这边则是**顺序** await 三个请求（详情 → 歌曲 → 专辑），三次往返串成一条线，最后一件事回来页面才有内容。

**改动（三层各一条）**

| 层 | 改动 | 理由 |
|---|---|---|
| 服务端 `AudioMetadataService.FillDurationsAsync` | 库里已有值就**不再探测文件**，只补"时长为空/0"的歌 | 读接口的职责是"补未知"；修正库里不对的值有扫描兜底（写入端已统一向下取整，2026-09-23 那批文档里的 1 秒偏差问题已在源头修掉） |
| 客户端 `ArtistDetailViewModel` | 详情 / 歌曲 / 专辑**并行**发出，谁先回来谁先上屏；歌曲**分页懒加载**（页大小 20） | 首屏要的是"页面什么时候有内容"，不是"能不能一次全拿到" |
| 客户端 `ArtistDetailPage.xaml` | `RemainingItemsThreshold="5"` + `RemainingItemsThresholdReachedCommand`，底部转圈只在真取下一页时出现 | 滚到离底部 5 行自动取下一页；全部加载完不留多余元素 |

**懒加载引出的两个必须一起处理的点**（不处理就是新 bug）：

1. **队列完整性（第一版做错了，见下方"返工"）**：队列里只有已加载的 20 首时，"下一首"听完这 20 首就没了 —— 本项目对"队列不完整"特别敏感（队列长度为 1 时循环/随机都在原地打转）。所以点歌/播放全部之后必须把剩余页补进队列。
2. **空列表直接返回**：`RemainingItemsThreshold` 在空列表/列表不足一屏时也会触发，不挡住就会对着服务端空转。另外翻页按 `Id` 去重：翻页期间有人播放（按播放量倒序的分页顺序会变）可能让同一首跨页出现。

**返工：补齐不能在点歌路径上等（2026-09-23 真机反馈"点了另一首会先放一秒上一首"）**

第一版把补齐写成了"播放前 `await EnsureAllSongsAsync()`"，于是**点击路径上多了一次网络请求**：等待的那几百毫秒里上一首还在响，用户听到的就是"我点了另一首，怎么还在放上一首"。这是本次改动自己引入的回归（改之前 `PlaySong` 是同步的，切歌是瞬时的）。

正确做法：**出声优先，队列随后补**

| 点 | 做法 |
|---|---|
| 点击路径 | 只用**已加载**的歌 `PlayQueue` → 立刻换音源、立刻跳播放页，路径上不 await 任何网络 |
| 补齐 | 跳转之后在后台取剩余页，`PlayerService.AppendToQueue(songs, 期望来源名)` 追加到队列尾部 |
| 防串台 | `AppendToQueue` 只在**队列来源没变**时追加（来源名 = 歌手名/歌单名）：用户已经去点别的列表了，就把这次结果丢掉，否则上一批的歌会混进新队列 |
| 去重 | 追加时按 `Id` 去重（同翻页那条理由） |

**验证（真机 + logcat 时间戳）**

| 项 | 结果 |
|---|---|
| 点歌不再等网络 | 日志 `PlayAt: called index=2, queueCount=20` —— 入队时队列就是"已加载的 20 首"，说明点击路径没等补齐请求；紧接着 103ms 内发出换源（`PlayAt: 远程音源 url=…`） |
| 队列随后补全 | 打开队列浮窗：被点的那首是第 3 项（带 ▶），底部「**共 36 首**」✅ |
| 界面 | 播放页正常、切歌正常（另有一条既有的 `spurious MediaEnded … recovering` 日志，与本改动无关，是切源时旧源的结束事件被识别为误报后自恢复） |

**一条教训**：**"播放"这类用户按下去就要有反应的动作，路径上不能有网络等待** —— 需要的数据要么提前取好，要么事后补，绝不能让它挡在出声前面。

**没验到的（诚实记录）**：库里当前没有"时长为 0"的歌，所以"补未知时长"那条分支这次没有被实际触发 —— 代码路径本身没改，只是入口条件从"没进过缓存"收紧成"库里没有值"；另外"取下一页失败后再滚一次自动重试"也没有在真机上人为制造失败来验。

**发行时间以文件标签为准（ATL 优先，库里其次）（2026-09-23，先于上一条的换库）**

需求：专辑的发行时间尽量从标签读，其次才用库里存的。

**先查清了一件事**（决定了这件事的收益）：拿实例探了标签的实际内容 ——

| 文件 | 标签类型 | 能拿到什么 |
|---|---|---|
| `Ado - ルル（rule）.flac` | Xiph (FLAC) | `Tag.Year=2024`，`DATE=2024`（**只有年**） |
| `Ado - 向日葵.MP3` 等一批 mp3 | ID3v1+v2 | `Tag.Year=0`，**连 TDRC/TYER/TDAT 都没有** |

结论有两条：① 这批文件里**没有比"年"更精确的发行时间**可读（TagLib 的通用标签 API 也只暴露 `Year`，FLAC 的 `DATE`、ID3v2.4 的 `TDRC` 即使带月日也取不到）；② 库里那些**没有发行日期的专辑，其文件标签也没有年份** —— 所以"优先取标签"对**当前这个库不会有可见变化**（不是代码没写对，是数据里确实没有）。

仍然按需求实现，因为它解决的是**将来会发生的三类偏差**：文件重打标签后（加了/改了年份）、专辑是从不写年份的入口进来的、或库里那份被改错了。

**实现**：`AudioMetadataService.FillAlbumReleaseDatesAsync(IList<AlbumDto>)`，接在 `CatalogService` 的专辑列表与单张读接口上（与 `FillDurationsAsync` / `FillPlaylistCoversAsync` 同一套模式）：

- 对每张专辑读其歌曲对应文件的 `Tag.Year`（取第一个有效年份，坏文件跳过），**每进程每张专辑只读一次**（静态缓存）；
- 文件有年份 → 用它（存成该年 1 月 1 日）；**没有 → 沿用库里的值**（即"其次用数据库"）；
- 发现与库里不一致时**顺手把库里改过来**（自愈），这样 App 和后台看到的是同一个值，不会"列表一个样、编辑框另一个样"—— 与时长/封面的既有做法一致；
- ⚠️ **只在年份不同时覆盖**：后台手工填的精确日期（如 `2024-05-15`）年份一致就保留，不会被文件里"只有年份"的信息降级成 `2024-01-01`。

**实测**（只改数据库，不动音乐文件；测完已还原）

| 场景 | 结果 |
|---|---|
| 文件标签年=2024，把库里改成 2001 | 接口返回 **2024-01-01**，并且**库里被自愈回 2024-01-01** ✅ |
| 文件无年份，库里设 2019-03-03 | 接口返回 **2019-03-03**（正确回退到库里的值）✅ |
| 库里设 2024-05-15（与文件年份一致的手工精确日期） | 接口返回 **2024-05-15**，未被降级 ✅ |

**这条不需要重启客户端**（纯服务端读取逻辑，刷新列表即可生效）。

## V2.4 歌单统计信息（播放次数）+ 歌单内搜索

> 状态：**已完成**。`PlaylistDto.PlayCount` 与 `PlaylistService.SearchSongsAsync` 均已上线（本节无独立实施记录）。

### 3.4.1 背景

歌单详情页现在只显示歌曲数和收藏人数（`PlaylistDto` 的 `TrackCount`、`CollectorCount`），
缺"这个歌单总共被播放了多少次"——这是用户判断歌单热度最直观的指标，也是 V2.12 推荐专区的输入之一。
同时大歌单（几百首）没有搜索，找一首歌只能靠翻。

### 3.4.2 设计方式

**统计口径**：歌单播放次数 = 该歌单内全部歌曲 `PlayCount` 之和（`PlaylistSongs` join `Songs` 求 `SUM`）。
`Song.PlayCount` 已由 `RecordPlayAsync` 累加，无需改造埋点。

**接口**：

- `PlaylistDto` / `PlaylistDetailDto` 增加 `PlayCount`（`long`，默认 0）。
- 新增 `GET /api/playlists/{id}/songs?keyword=&page=1&pageSize=20`
  → 返回 `PagedResult<SongDto>`，关键词走 `ILike`，命中标题/歌手/专辑。

**交互**：歌单详情页头部统计条补"播放次数"；列表页排序增加"播放量"选项；

### 3.4.3 开发选型

| 方案 | 取舍 |
|---|---|
| **A. 聚合查询**（选中） | 每次查歌单时 `SUM(Songs.PlayCount)`。数据永远准确，零维护成本。代价是超大歌单有一次 join |

顺带落一份冗余列并定时刷新——不要一开始就背上维护成本。

### 3.4.4 开发思路

1. `Core/Dtos/MusicDtos.cs`：`PlaylistDto`、`PlaylistDetailDto` 增加 `PlayCount` 字段（放末尾并给默认值，避免破坏现有构造）。

3. `Api/Controllers/PlaylistsController.cs`：新增 `GET {id:long}/songs`。

## V2.5 账号信息 + 安全中心

> 状态：**已完成**（含 §3.5.6「头像改为内置头像」，V2.9.3 改动记录）。

### 3.5.1 背景

后端 `PUT /api/auth/me` 已经能改昵称/简介/性别/头像，但客户端**没有任何编辑入口**，用户注册后就改不了资料。
同时 `User` 实体没有 Email 列，也没有修改密码的接口——账号被盗后无法自助改密，是明显的短板。
另外 JWT 是无状态的，改密后旧 token 在过期前仍然有效，安全中心必须处理这个"改了密码但别人还能用"的窗口。

### 3.5.2 设计方式

**数据层**：新增迁移 `AddUserEmailAndTokenVersion`，`Users` 表补两列（P0 之后走迁移，不再手写 DDL）

- `Email text NULL`
- `TokenVersion int NOT NULL DEFAULT 0`
- 同迁移内建 `EmailVerification` 表

**接口**（均在 `AuthController`，`[Authorize]`）

| 接口 | 用途 |
|---|---|
| `PUT /api/auth/me`（已有） | 改昵称、性别、简介、头像 URL |
| `PUT /api/auth/password` | 传旧密码 + 新密码，校验旧密码后 BCrypt 重哈希 |
| `POST /api/auth/email/code` | 发送邮箱验证码（SMTP 未配置时返回明确提示） |
| `PUT /api/auth/email` | 提交邮箱 + 验证码完成绑定 |

**改密后旧 token 失效**：签发 token 时写入 `tv` 声明（`TokenVersion`）；`TokenService.CreateToken` 增加该声明，
鉴权校验环节比对数据库中当前值，不一致即判为失效。改密时 `TokenVersion += 1`。

**头像上传**：复用现有 `POST /api/media/upload?kind=avatar`，前端拿到 URL 后写入资料，不新增接口。

**邮箱验证码**：6 位数字，10 分钟有效，5 分钟内最多发 3 次；未配置 SMTP 时前端隐藏邮箱绑定入口并在后台给出提示，
避免 Docker / 安装包形态下功能"点了没反应"。

### 3.5.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 密码哈希 | BCrypt（`BCrypt.Net-Next`，已在用） | 保持一致，不引入第二套 |
| 邮件发送 | MailKit | `System.Net.Mail.SmtpClient` 官方已标记过时 |
| 验证码存储 | 落库 `EmailVerification` 表 | 内存缓存在 API 重启后失效；Docker 部署每次重启概率高 |
| token 失效 | `TokenVersion` 列 + `tv` 声明 | 无状态 JWT 下代价最小的方案，不需要维护黑名单 |
| SMTP 缺失 | 功能开关而非硬失败 | 部署形态多样（Docker / Windows 安装包），不能让缺 SMTP 阻断启动 |

### 3.5.4 开发思路

1. `Core/Entities/User.cs` 加 `Email`、`TokenVersion` 属性，新增 `EmailVerification` 实体。
2. `dotnet ef migrations add AddUserEmailAndTokenVersion`（P0 已就绪，直接生成迁移）。
3. `Application/AuthService.cs` 增加 `ChangePasswordAsync`、`SendEmailCodeAsync`、`BindEmailAsync`。
4. `Api/Auth/TokenService.cs` 的 claims 增 `tv`；校验侧比对数据库版本。
5. `Api/Controllers/AuthController.cs` 增三个接口。
6. 客户端：账号页（复用 `SettingsPage` 的布局风格）+ 安全中心页（改密表单、邮箱绑定表单、验证码倒计时）。
7. `MusicApiService` 增对应方法，全部走 `Abs(...)`。
8. 后端重建重启，用 `/openapi/v1.json` 核对字段。

## V2.6 本地音乐库（离线播放本地文件）

> 状态：**已完成**。本地曲库存储与两端扫描（`AndroidLocalMediaScanner` / `WindowsLocalMediaScanner`）均已上线（本节无独立实施记录）。

### 3.6.1 背景

用户希望在没有网络时也能听自己设备里已有的音乐。这类音乐**不在服务端曲库**，也没有 `songId`，
所以它的定位是纯本地能力：本地扫描、本地存储、本地播放，与服务端零交互。
这也是整个 V2.x 里第一个需要在客户端引入本地数据库的功能——它同时是 V2.7（缓存）和 V2.11（补报队列）的地基。

### 3.6.2 设计方式

**本地表**（SQLite，`yinyan-local.db` 放 `FileSystem.AppDataDirectory`）

```sql
CREATE TABLE LocalSong (
    Id                INTEGER PRIMARY KEY AUTOINCREMENT,
    FilePath          TEXT NOT NULL UNIQUE,   -- 去重键：同一文件重复扫描不入库
    Title             TEXT NOT NULL,
    ArtistName        TEXT,
    AlbumName         TEXT,
    DurationSeconds   INTEGER,
    CoverPath         TEXT,                   -- 内嵌封面抽出的本地文件
    DateAddedUtc      TEXT NOT NULL,
    LastPlayedAtUtc   TEXT,
    LocalPlayCount    INTEGER NOT NULL DEFAULT 0  -- 只记本地，永不上报
);
```

**扫描**

- Android：`READ_MEDIA_AUDIO`（API 33+）/ `READ_EXTERNAL_STORAGE`（≤32），运行时动态申请；
  通过 `MediaStore.Audio.Media` 查询，**不要递归遍历目录**（慢且容易被分区存储限制挡住）。
- Windows：文件夹选择器让用户指定目录，再枚举音频扩展名（与 Scanner 保持一致：mp3/flac/m4a/wav/ogg）。
- 元数据复用 `TagLibSharp`（Scanner 已在用）读标签与内嵌封面，保证两端解析口径一致。

**播放**：`PlayerService` 目前只吃远程 URL（全部走 `ApiConfig.Absolute`），需要新增本地源分支：
本地歌传文件路径，Android 端 `CustomForwardingPlayer`（ExoPlayer）按 `file://` / `content://` 出源。
播放队列、锁屏通知、进度条沿用现有实现。

**不上报**：本地歌触发播放时**不得调用** `POST /api/songs/{id}/play`（没有 songId，也不该上报），
只累加 `LocalPlayCount`。

**不进在线歌单**：本地歌的菜单里隐藏"加入歌单"，或提示仅可加入本地歌单，避免换设备出现空歌。

### 3.6.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 本地数据库 | `sqlite-net-pcl` | 轻量、属性标注、MAUI 常规选择；不引 EF Core SQLite（重，且撑大 android/windows 包体） |
| 元数据 | `TagLibSharp`（已在 `Directory.Packages.props`） | 与 Scanner 同一解析口径，不新增依赖 |
| Android 扫描 | MediaStore 查询 | 比目录遍历快一个量级，且兼容分区存储 |
| Windows 扫描 | 文件夹选择器 + 枚举 | 避开 `broadFileSystemAccess` 的商店审核麻烦 |
| 播放 | MediaElement 本地源 + Android ExoPlayer `file://` | 不引入第二个播放内核 |

### 3.6.4 开发思路

1. 引入 `sqlite-net-pcl`，建 `LocalLibraryStore`（初始化连接 + 建表 + 版本位）。
2. 权限与扫描：Android 动态权限 + MediaStore；Windows 文件夹选择。
3. 元数据解析：`TagLibSharp` 抽标题/歌手/专辑/时长/内嵌封面（封面落 AppData）。
4. `PlayerService` 增加本地源分支（注意 `#if WINDOWS` / `#elif ANDROID` 对称）。
5. UI：本地音乐页（列表、搜索、排序）、播放页兼容本地歌（封面、标题、专辑名）。
6. 本地播放计数：播放结束累加 `LocalPlayCount`；**禁止**调用任何上报接口。
7. 文件失效处理：播放时文件不存在 → 标记并提示移除，不要静默失败。

## V2.7 歌曲缓存与离线播放

> 状态：**已完成**（2026-09-22，见 §3.7.6 实施记录）。

### 3.7.1 背景

V2.6 解决了"设备里本来就有的歌"，这一版解决"服务端曲库里的歌下载下来离线听"。
区别在于：缓存歌曲**有 `songId`**，因此它是 V2.11 补报的对象，也是统计口径的一部分。

### 3.7.2 设计方式

**缓存索引**（同一个 SQLite 库）

```sql
CREATE TABLE CachedSong (
    SongId         INTEGER PRIMARY KEY,  -- 服务端 songId
    FilePath       TEXT NOT NULL,
    SizeBytes      INTEGER NOT NULL,
    CachedAtUtc    TEXT NOT NULL,
    LastAccessUtc  TEXT
);
```

**下载**：`HttpClient` 流式下载 `/media/audio/<文件名>`（静态托管天然支持 Range，可做断点续传），
边下边写文件，**不要一次性读进内存**。并发上限 3，失败指数退避重试 2 次。

**离线判定**：`Connectivity.Current.NetworkAccess != Internet` 或请求失败时，
播放优先读本地缓存文件；有网时优先播远程（保证听到的是服务端最新版本）。

**容量上限**：设置页新增"缓存上限"输入（单位 GB），校验范围 `0 < x ≤ 10`。
下载前预检 `已用 + 预计大小 > 上限` → 拒绝并提示"去设置页清理或调高上限"。
**达到上限即停止缓存，不自动删除旧缓存**。下载途中才跨过上限的，允许当前这首下完，下一首再拒绝。

**清理**：设置页提供"按歌清理"和"清空缓存"，删除文件同时删索引行。

### 3.7.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 下载 | `HttpClient` + `HttpCompletionOption.ResponseHeadersRead` 流式写 | 避免大文件占满内存 |
| 断点续传 | Range 头 | 静态文件中间件默认支持，实现成本低 |
| 容量统计 | SQLite 聚合 `SUM(SizeBytes)`，启动时与实际文件对账 | 比每次遍历目录快 |
| 上限存储 | `Preferences`（沿用 `ApiConfigStore` 的读写模式） | 单一配置值，不必入库 |
| 离线判定 | `Connectivity`（MAUI 内置） | 不引入第三方网络库 |

### 3.7.4 开发思路

1. 建 `CachedSong` 表与 `CacheStore`（增删改查、容量统计、对账）。
2. 下载服务：队列 + 并发 3 + 流式写 + 断点续传 + 失败重试。

**与设计稿的偏差（都是实现期发现必须调整的）**

1. **`CachedSong` 增加了冗余展示字段**（Title / ArtistName / AlbumName / CoverUrl / AudioUrl / DurationSeconds）。
   原因：缓存管理页在**离线**时也要列得出歌名歌手；`AudioUrl` 还必须保留，否则"有网优先远程"（TC-2.7-03）拿不到远程地址。

   原因：既然后续版本要建表，不如本版一次把表与入队路径做完，避免中间版本丢数据。
3. **上限的默认值与下限**：默认 **5 GB**，合法区间 **0.1 ~ 10 GB**（`0` 会让功能事实上不可用，按 TC-2.7-06 必须拒绝）。
4. **下载不走 DI 里的 HttpClient**：单例 HttpClient 的 `Timeout=30s` 会掐断大文件下载，改为下载服务自建客户端（20 分钟超时，不带 Bearer —— `/media/audio` 是静态托管）。
5. **落地文件名冲突兜底**：目标文件被占用（缓存正在被播放时删缓存 → Windows 删不掉）时改用带时间戳的备用名，而不是把整次下载判失败。
6. **回退只尝试一次**：`MediaFailed` 时若本机有缓存则改用缓存文件重播，但一首歌只回退一次，避免缓存文件本身损坏时反复切源。

**验收期按用户要求新增：播完自动缓存（2026-09-22 定案）**

原实现只支持**手动**缓存（歌曲菜单「缓存到本地」），播放路径对缓存只读不写。用户验收时要求补上"边听边自动缓存"，并定下三条策略，均已实现：

| 策略 | 落点 |
|---|---|
| **只缓存完整听完的** | 挂在 `PlayerService.HandleMediaEndedAsync()` 里 —— `MediaEnded` 只在自然播完时触发，**手动切歌不会走到**，所以这条由调用时机天然保证（无需比对进度）；必须在切歌前取 `Current`，否则 NextAsync 已经把当前歌换掉了 |
| **只在 WiFi 下自动存** | `CacheDownloadService.IsOnWifi()`：要求 `NetworkAccess == Internet` 且 `ConnectionProfiles` 含 `WiFi`；**判断不出来一律返回 false**（保守：宁可漏缓存，也不在移动网络上偷偷下载整首歌） |
| **撞上限静默跳过 + 计数** | 新增 `CacheEnqueueStatus.RejectedNoSpace`（与通用 `Rejected` 分开，专供自动缓存计数）；次数存 `CacheStore.AutoCacheSkippedCount`，缓存管理页显示"有 N 首因超过上限没有自动缓存"，`ClearAsync()` 时归零。**"绝不自动删旧缓存"不变** |

配套：`EnqueueAsync(…, silent: true)` 让自动缓存**不弹完成提示**（不打扰听歌，进度事件照发）；开始下载前延迟 2.5s 避开"下一首的缓冲"；新增开关 `CacheStore.AutoCacheEnabled`（**默认开**），设置页「歌曲缓存」区块可关闭。

**本版刻意不做**：封面文件缓存、播放进度上报（V2.10）、补报 flush（V2.11）、LRU 自动淘汰（用户已定案"绝不自动删旧缓存"）。

**真机验收期暴露并顺手修掉的工程缺陷：Android 明文 HTTP 策略"Debug 全开"从未生效**

- 现象：Debug 包（真机 Android 16）在设置页填 `http://<局域网IP>:5116` 点「测试连接」→ 只有一句
  `连不上：Connection failure`；而**同一台设备、同一个 App uid** 用 `run-as … curl` 请求同一地址 → 200。
- 根因：`network_security_config.xml` 里的
  `<debug-overrides><base-config cleartextTrafficPermitted="true"/></debug-overrides>` 是**无效配置** ——
  Android 官方文档明确 `<debug-overrides>` 的合法子元素只有 `<trust-anchors>`（只用于追加调试证书），
  它改不了明文策略。所以从 V0.1 起 Android 端**只能**连 nsc `domain-config` 白名单里的地址。
  此前没暴露，是因为 Debug 包 Android 默认走 HTTPS 域名，从没人在真机连过局域网明文后端。
  另外 `curl` 是 native 实现、**不检查** Android 明文策略，而 App 走 Java 栈（受策略管辖），
  "curl 通"不能证明"App 通"——这条是排查时最容易走弯路的地方。
- 修复（明文许可**只认 nsc**：声明了 `networkSecurityConfig` 后 manifest 的
  `android:usesCleartextTraffic` 会被系统忽略，所以只能换文件）：
  1. 新增 `Platforms/Android/Resources/xml/network_security_config_debug.xml`（`base` 明文全开）；
  2. `network_security_config.xml` 恢复严格（`base` 显式 `false` + 生产域名 `false` + 本地三项 `true`），
     并删掉写死的老开发机 IP；
  3. `AndroidManifest.xml` 改 `android:networkSecurityConfig="${nscRes}"`；
  4. csproj 用 `AndroidManifestPlaceholders`（`${nscRes}`）按构建配置选用两个文件之一。
- 配套增强（保留）：设置页「测试连接」改用**双网络栈对照探测** ——
  默认 `HttpClientHandler`（Java 栈，受系统策略管辖）与 `SocketsHttpHandler`（托管栈，不走 Java 策略）
  各试一次，并把完整异常链显示出来。正是这条诊断拿到了
  `IOException: Cleartext HTTP traffic to 10.104.242.85 not permitted` 的直接证据。

**验证**：Windows 目标 `net10.0-windows10.0.19041.0` 编译通过（exit=0，无 error）；Android 目标编译通过并安装到真机，局域网明文连接已验证可用。真机端到端（缓存→飞行模式播放→恢复联网）待验收。

**真机验收期暴露并修掉的回归：播放内核被二级页面带走（"有进度没声音"）**

- 现象：播放在线音乐时**通知栏进度条在动，却完全没有声音**。
- 根因：本版新增的 `CacheManagePage`（以及 V2.6 的 `LocalMusicPage`）自带 `MediaElement`
  并在进入时调用 `PlayerService.AttachPlayer` **抢走**播放器；页面退出后元素销毁、底层 ExoPlayer 被
  `Release`，而 `PlayerService` 是单例、字段里还攥着那个已释放的实例 —— 之后所有播放都写到一个
  已销毁的元素上：不报错、不出声，只有系统通知栏按旧状态画进度。
  真机 logcat 铁证：`ExoPlayerImpl: Release` 之后紧跟
  `Cannot access disposed object … IExoPlayerInvoker`，而 `MediaSessionService` 仍报 `PLAYING`。
- 修复（确立"一个长期播放内核"的约定）：
  1. `PlayerService.AttachPrimaryPlayer` —— `MainPage` 用它登记**长期存活**的内核；
  2. `AttachPlayer` 改为**只在还没有主内核时**才接管（覆盖"未登录直达本地音乐/缓存管理"场景）；
  3. `ReleasePlayer` —— 页面退出时归还：把播放**迁回内核续播**（同曲、同位置、同播放状态）；
  4. `OnPlayerElementGone` —— 元素 `Handler` 变 null（已销毁）时立刻清空 `_player`/`_exoPlayer`，
     杜绝悬空写入；
  5. 迁移重载走 `PlayAt(index, skipReport: true)`：换内核不是新的一次播放，**不重复计数/上报**。
- 结论性约定（后续新增任何带 `MediaElement` 的页面都要遵守）：**只有 `MainPage` 登记主内核；
  页面级元素只在没有主内核时接管，且必须在 `OnNavigatedFrom` 调 `ReleasePlayer`。**

## V2.8 定时任务扫描目录音乐入库

> 状态：**已完成**（2026-09-22，见 §3.8.6 实施记录 / §3.8.7 验收后追加修复；该节末尾另列有**明确不在本版范围**的遗留项）。

### 3.8.1 背景

目前把音乐放进曲库只有两条手动路径：服务器上的 `Scanner` CLI，或调 `POST /api/admin/import?dir=`
（需要 admin token）。运维往挂载目录丢一批新歌之后还得记得去触发一次，忘了就一直不生效。

> **后台侧已具备手动能力**：`v2_admin_web` 初版的 `SystemTasks.vue`（路由 `/system/tasks`，标题"导入与扫描"）
> 已经能手动触发 `POST /api/admin/import?dir=`、`POST /api/admin/scan-durations` 与 seed。
> 因此 V2.8 的后台部分只需**补上定时状态展示与开关**，工作集中在服务端定时器。

### 3.8.2 设计方式

在 API 进程内挂一个 `BackgroundService`：按配置间隔扫描 `Media:MusicDirectory`，复用现有
`AdminService.ImportFromDirectory` 的解析与去重逻辑（按 `AudioUrl` 去重，已存在则跳过）。

**配置**：`Media:ScanIntervalMinutes`（默认 60，0 或负数 = 关闭），支持环境变量 `Media__ScanIntervalMinutes`；
Windows 安装形态下会被 `%ProgramData%\YinYanMusic\appsettings.json` 覆盖（V2.3 那套配置层已就位）。

**约束**：

- 启动后延迟一个间隔再跑第一次（不阻塞启动，避免大目录拖慢健康检查导致 CI 部署判定失败）。
- 单实例保护：上一轮未结束则跳过本轮（当前部署为单容器/单机，不做分布式锁）。
- 只做增量：目录无变化时导入结果 `updated = 0`，不写库。
- 后台管理端提供"立即扫描"按钮与上次扫描时间/结果展示（挂在 V2.3 的后台）。

### 3.8.3 开发选型

| 方案 | 取舍 |
|---|---|
| **原生 `BackgroundService`**（选中） | 零依赖，随进程生命周期，Windows 服务与 Docker 两种形态都天然支持 |
| Quartz.NET | 支持 Cron 与持久化，但本项目只需要"每隔 N 分钟"，引入调度框架属于过度设计 |

### 3.8.4 开发思路

1. `appsettings.json` 增 `Media:ScanIntervalMinutes`，CI 与 Dockerfile 的默认值对齐。
2. 新建 `Api/Jobs/DirectoryScanJob.cs`（`BackgroundService`），注入 `IServiceScopeFactory` 取 `IAdminService`。
3. `Program.cs` 注册 `AddHostedService<DirectoryScanJob>()`。
4. 扫描结果写日志（total / updated / skipped），并更新一份内存状态供后台查询。
5. 后台侧：在已有 `SystemTasks.vue` 上补"上次扫描时间/结果"展示与定时器开关，**不重做导入页**
   （手动导入与扫描时长按钮初版已具备）。
6. 与 V2.7 缓存的关系：新增歌曲不影响已缓存文件，无需联动。

2. **新增 `Media:ScanRecursive`（默认 true）**。设计稿只说"扫描目录"；实际运维按专辑分子目录丢文件，递归才符合预期。URL 仍是 `/media/audio/<相对路径>`，静态托管与 `AudioMetadataService` 都能正确往返。
3. **新增 `Media:ScanOnStartup`（默认 false）**，把"启动后延迟一个间隔"做成可配置项；默认关是为了不挡住健康检查（TC-2.8-05）。
4. **扫描顺带补时长**（计入 `updated`）。设计稿只要求增量导入新歌，但历史导入路径留下的 0 时长老数据在歌单里同样是隐形的。这是收敛的：补齐后再跑就是 `updated = 0`，不影响 TC-2.8-02。
5. **单实例保护收进 `ScanRunner`，覆盖"定时 + 后台手动"两条路径。**
   只保护定时器是不够的：后台手动触发若与定时轮撞上，两条路径会同时读写同一批文件。实现期自测时确认了这个缺口 —— 手动接口最初只**读** `IsRunning` 不置位，并发触发不被拦截；改成两条路径共用同一个信号量后才真正串起来。
6. **状态不持久化**。`ScanState` 只在进程内存：重启后"上一轮结果"已不代表任何东西，展示陈旧数据比留空更坏。后台开关同理（重启回到配置文件的值），这句在界面上明写。
7. **间隔配 0 时也允许打开开关**：用默认 60 分钟兜底 —— 否则开关"打开了却不跑"，比不给开更费解。

## V2.9 歌单与歌曲评论

> 状态：**已完成**（见 §3.9.6 实施记录，及 §3.9.7 / §3.9.8 两次改动记录）。

### 3.9.1 背景

曲库与歌单目前是单向消费，用户之间没有任何互动入口。评论是成本最低、也最能带动留存的一层，
同时它需要"审核/删除"的运营动作——这正是 V2.3 后台必须先落地的原因。

### 3.9.2 设计方式

**数据**（服务端 PostgreSQL，迁移 `AddComments` + `AddCommentThreading`）

```sql
-- 由迁移生成，此处为结构参考（含 V2.9.1 多层回复新增的三列）
CREATE TABLE "Comments" (
    "Id"         bigserial PRIMARY KEY,
    "TargetType" text NOT NULL,        -- 'song' | 'playlist'
    "TargetId"   bigint NOT NULL,
    "UserId"     bigint NOT NULL,
    "ParentId"   bigint NULL,          -- 回复的父评论；null = 主评论
    "RootId"     bigint NULL,          -- 所属主评论；主评论自己为 null（物化线索，见 3.9.7）
    "Depth"      integer NOT NULL DEFAULT 0,   -- 主评论 0，逐层 +1（最多 4）
    "Content"    text NOT NULL,
    "LikeCount"  integer NOT NULL DEFAULT 0,
    "IsHidden"   boolean NOT NULL DEFAULT false,   -- 后台软隐藏
    "IsDeleted"  boolean NOT NULL DEFAULT false,   -- 作者已删但下面还有回复 → 占位楼
    "CreatedAt"  timestamp with time zone NOT NULL
);
CREATE TABLE IF NOT EXISTS "CommentLikes" (
    "CommentId" bigint NOT NULL, "UserId" bigint NOT NULL,
    CONSTRAINT "PK_CommentLikes" PRIMARY KEY ("CommentId", "UserId")
);
-- 索引：(TargetType, TargetId, CreatedAt) 列表、(UserId, CreatedAt) 限流、(RootId, Id) 取整棵子树
```

**接口**

| 接口 | 说明 |
|---|---|
| `GET /api/comments?targetType=&targetId=&page=` | 评论列表（隐藏的对普通用户不可见）。主评论分页，每条带上整棵回复子树 |
| `GET /api/comments/{id}/replies?page=` | 某条主评论下全部回复的扁平分页（"展开全部"，超过 200 条才用得上） |
| `GET /api/comments/count?targetType=&targetId=` | 可见评论**总数（主评论 + 回复）**：App 的「更多」菜单用它拼「查看评论：(N)」，面板标题也用它。注意与列表的 `total` 口径不同（那个只数主评论） |
| `POST /api/comments` | 发表 / 回复（内容 1–500 字，同用户 10 秒一条，层级最多 5 层） |
| `DELETE /api/comments/{id}` | 作者本人删除（下面还有回复时保留占位楼） |
| `POST /api/comments/{id}/like` / `DELETE` | 点赞 / 取消（按 `CommentLikes` 去重） |
| `GET /api/admin/comments` / `PUT /api/admin/comments/{id}/hidden` | 后台审核（V2.3 后台加页面） |

**客户端**：三个入口 —— 播放页顶栏、歌单详情页按钮行、以及歌曲「更多」菜单里的
「查看评论：(N)」（取不到数时退化成不带数字的「查看评论」，入口不消失）。
面板从底部弹出（遵循 1.3 节第 5 条：一律 `SongMenuHelper.AttachOverlay`，不替换 `page.Content`），
头像在昵称左侧（无头像回退昵称首字），支持发表、**多层回复**、删除自己的、点赞；
缩进最多到第 4 层，再深就靠"回复 @某人"点明从属关系。

**级联**：歌曲或歌单被删除时，其评论一并删除，避免孤儿数据。

### 3.9.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 回复层级 | **真树**（`ParentId` 自引用）+ `RootId`/`Depth` 物化，**最深 5 层**（`Depth` 0–4） | V2.9.1 起改动：真实评论不可能只有一层。物化 `RootId` 让"取一整页主评论的全部回复"是一条 `RootId IN (…)` 索引查询，既不用递归 CTE、也不用应用层逐层捞 |
| 子树条数上限 | 每条主评论每页最多带回 200 条子孙，超出走 `/replies` 分页（两处同为 200） | 热门评论动辄上千条。两处取同值是为了让客户端第一次"展开全部"拿到的正是列表已给过的那一批，不会出现"越展开越少" |
| 作者删除 | 楼下还有回复 → 保留**占位楼**（`IsDeleted`：正文清空、作者不再返回）；没有回复 → 物理删除 | 连子回复一起删等于替别人删了帖子；叶子评论留空壳又是垃圾数据 |
| 后台删除 | 物理删除（整棵子树一并带走） | 违规内容不该在库里留存；只想让它不可见就用"隐藏" |
| 点赞去重 | 独立 `CommentLikes` 表 | 复合主键天然幂等，不依赖应用层判断 |
| 隐藏 vs 删除 | `IsHidden` 软隐藏 | 保留审计痕迹，后台可恢复；被隐藏的评论其整棵子树对普通用户也不再出现 |
| 内容渲染 | 纯文本，不渲染 HTML | 避免 XSS；不引入 Markdown 渲染器 |

### 3.9.4 开发思路

1. `Core/Entities` 增 `Comment`、`CommentLike` 实体；`dotnet ef migrations add AddComments`
   （含外键与索引 `TargetType+TargetId+CreatedAt`）。
2. `Core/Dtos` 增 `CommentDto`、`CreateCommentRequest`。
3. `Application` 增 `CommentService`（列表、发表、删除、点赞、后台审核），频率限制放在服务层。
4. `Api` 增 `CommentsController` 与 `AdminController` 的审核接口。
5. `SongService.DeleteAsync` / `PlaylistService.DeleteAsync` 增加评论级联清理。
6. 客户端 `MusicApiService` 增方法；`SongMenuHelper` 增评论面板方法（复用弹层积木）。
7. 后台：评论管理页（搜索、隐藏/恢复、删除）。

**取舍与已知边界**

- 占位楼的正文**在库里就已清空**，所以后台按内容关键词搜不到它 —— 这是"作者删了就该搜不到"的应有之义，不是漏洞；要审这条楼得按目标对象翻页找。
- 占位楼是"删除那一刻楼下还有回复"留下的。此后若它的子孙也被逐条删光，这条占位楼会作为没有下文的空楼层留在列表里（无害，但会慢慢积累）。
- 列表里"每条主评论 200 条子孙"的预算在**同一页内是共享的**：某条主评论一家占满预算时，同页其他主评论会少拿回复 —— 但各自的 `replyCount` 由独立聚合查询给出，客户端仍会显示"共 N 条"并提供"展开全部"，降级可见且可恢复。
- 后台「删除」仍是物理删除（整棵子树一起走），与作者删除的"占位楼"语义不同，这是有意的（见 3.9.3）。

### 3.9.8 V2.9.2 头像、「更多」菜单入口与评论数口径（改动记录）

| 改动 | 内容 |
|---|---|
| 客户端 | 评论行显示**头像**（昵称左侧，主评论 34dp / 回复 26dp）；无头像回退成昵称首字圆底；作者已删的占位楼不给头像。头像解析走 `ImageSourceFactory`，并按 URL 在**面板作用域**缓存 —— V2.5 的头像是 data URI（实测 48KB base64）且同一作者会重复出现 |
| 入口 | 歌曲「更多」菜单（`ShowMenuAsync`）与歌单详情页里手写的歌曲菜单都加上「查看评论：(N)」；取不到数就退化成不带数字的「查看评论」，**入口不消失**。本地歌没有 songId，两条路径都不会出现这一项 |
| 接口 | 新增 `GET /api/comments/count?targetType=&targetId=`，返回**可见评论总数（主评论 + 回复）** |

**为什么要单独一个计数接口**：列表接口的 `total` 只数主评论（回复跟着主评论一起翻页，进不了分页计数），
拿它当"评论数"会和用户直觉冲突 —— 只写 1 条主评论 + 3 条回复，用户认为那是 4 条评论。
所以菜单文案与面板标题统一用 `/count` 的口径，列表的 `total` 只负责翻页。
真实数据实测：歌单 3 = 1 条主评论 + 1 条回复 → `/count` 返回 2，而列表 `total` 是 1；
歌曲 8 = 1 条被作者删掉的**占位楼** + 3 条回复 → `/count` 返回 4，与列表装配出的节点数一致。

## V2.10 多端同步播放进度

> 状态：**已完成**（2026-09-25，见 §3.10.6 实施记录）。

### 3.10.1 背景

同一账号在手机上听到一半，回到 Windows 客户端要重新找、重新拖进度。
**语义确定为"断点续播"**：换设备从上次的位置继续，**不做**一台播放另一台实时跟随（后者需要长连接，量级翻倍）。

### 3.10.2 设计方式

**服务端表**（新增迁移 `AddPlaybackProgress`）

```sql
-- 由迁移生成，此处为结构参考
CREATE TABLE "PlaybackProgress" (
    "UserId" bigint NOT NULL, "SongId" bigint NOT NULL,
    "PositionSeconds" double precision NOT NULL,
    "UpdatedAtUtc" timestamp with time zone NOT NULL,
    CONSTRAINT "PK_PlaybackProgress" PRIMARY KEY ("UserId", "SongId")
);
```

**接口**：`PUT /api/me/playback/progress`（`{ songId, positionSeconds }`）、
`GET /api/me/playback/last`（返回最近一条及歌曲信息，供"继续播放"卡片使用）。

**客户端**：暂停、切歌、退出 App 时上报；播放中每 30 秒心跳上报一次。
启动时拉 `last`，首页/我的页展示"继续播放：xxx（02:15）"入口。
冲突处理：以 `UpdatedAtUtc` 最新者为准；上报失败不影响当前播放（异步、静默重试）。

**范围**：只同步服务端曲库的歌（有 `songId`）；本地音乐不参与（V2.6 定位）。

### 3.10.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 同步方式 | HTTP 轮询 + 事件触发上报 | 断点续播不需要毫秒级实时，不必引入 SignalR |
| 存储 | 每用户每歌一行（复合主键 upsert） | 天然去重，数据量为"用户 × 听过的歌"，可控 |
| 上报时机 | 暂停/切歌/退出 + 30s 心跳 | 平衡请求量与进度精度 |

### 3.10.4 开发思路

1. 新增 `PlaybackProgress` 实体并 `dotnet ef migrations add AddPlaybackProgress`；`Core/Dtos` 增 `PlaybackProgressDto`。
2. `Application` 增 `PlaybackService`（保存、取最近一条）。
3. `Api` 增 `MeController` 的两个接口（`[Authorize]`）。
4. 客户端：`MusicApiService` 增方法；`PlayerService` 在暂停/切歌/心跳处触发上报（失败静默）。
5. 首页/我的页增"继续播放"入口，点击带上整张上下文列表播放（1.3 节第 10 条）。

| TC-2.10-02 | 上报时机 | 切歌后立即查 last | 为新歌，位置接近 0 |
| TC-2.10-03 | 心跳 | 连续播放 2 分钟不操作 | 服务端位置随之更新 |

### 3.10.6 实施记录

**服务端**

| 项 | 落地 |
|---|---|
| 表 | `PlaybackProgress`（`UserId` + `SongId` 复合主键、`PositionSeconds`、`UpdatedAtUtc`），迁移 `20260925190805_AddPlaybackProgress` |
| 外键 | 对 `Songs` / `Users` 都是**级联删除**。3.10.2 的结构参考里没写外键，这里加上是有意的：歌被删时进度行随数据库一起消失，"继续播放"就不可能指向一首不存在的歌（TC-2.10-08 因此是**结构性成立**，而不是靠查询时兜底） |
| 索引 | `(UserId, UpdatedAtUtc)` —— "最近一条"就是按它取 |
| 服务 | `PlaybackService.SaveAsync`（先查后改/插，复合主键天然去重；覆盖语义 = 后写覆盖先写）与 `GetLastAsync`（按 `UpdatedAtUtc` 倒序取 1，同毫秒再按 `SongId` 兜底保证稳定；带完整 `SongDto` 让客户端能直接起播） |
| 接口 | **单独一个 `PlaybackController`**（`api/me/playback`，`[Authorize]`）而不是加进 `MeController`：路由一样，但不必动 `IMeService` 与它的假实现，改动面更小。`GET last` 没有记录时返回 **204** |

**客户端**

| 项 | 落地 |
|---|---|
| 上报时机 | 暂停（`OnIsPlayingChanged` 转 false，原来这段被 `#if ANDROID` 包着，现已改为跨平台）、切歌（切之前补报上一首的位置 + 新歌按其**实际起播位置**报一次）、播放中每 30 秒心跳（**搭在既有的 500ms 进度定时器上**，每 60 跳报一次，不新开计时器）、退出 App（`OnSleep` 尽力报一次，仅兜底） |
| 跳过条件 | 本地歌（`IsLocal` / Id ≤ 0）与未登录都直接跳过上报 —— 前者服务端不认识，后者白跑一趟还多一次 401（TC-2.10-05/06） |
| 失败处理 | 全部 fire-and-forget，失败只落日志；断网时播放完全不受影响（TC-2.10-04） |
| 续播 | `PlayerService.PlayQueueAt(...)` 复用**既有的** `_resumeAfterOpen` / `ResumeState`（原来只给"换内核迁移"用）：把定位交给 `OnMediaOpened` 去做，而不是在源还没打开时直接 Seek（那条路会丢 Seek，文件里早有注释） |
| 入口 | 首页首屏「继续播放」卡片（封面 + 歌名 + 歌手 + 上次位置），点它续播。3.10.2 写的是"首页/我的页"，本轮只落首页 —— 一个清晰入口即可，两处重复反而分散 |
| 入口的显示条件 | 三选一全部为"否"才显示：① 有进度记录；② 正在播的不是这一首；③ **进度的设备名 ≠ 本机名**（V2.12 加了设备名之后补的这一条，与 3.10.2「**换设备**接着听」的语义对齐 —— 进度就是本机自己报的，再弹"上次在「本机」听到"纯属噪音，TC-2.10-09）。设备名为空（老记录 / 老服务端）时**不**抑制，判断不了就不能假定同机，否则老记录会把入口永远藏掉（TC-2.10-10）。比较用上报时的同一个值（`IMusicApi.CurrentDeviceName`），避免"报的是 A、比的是 B"的漂移 |
| 上下文列表 | 点卡片不是只把这一首塞进队列，而是拉**这位歌手的歌**当上下文（全局约束 1.3 第 10 条：队列长度为 1 时"列表循环"的下一首等于自己）；歌手歌拉不到就退化成单曲队列，至少能续播 |

**两个会互相打架的地方（都已处理，别改回去）**

1. `PlayAt` 末尾那条"新歌上报"如果硬写位置 0，会把 `PlayQueueAt` 刚设好的续播点覆盖成 0 —— 用户再换设备就变成"从头发"。现在取 `_resumeAfterOpen?.PositionSeconds ?? 0`：普通切歌报 0（TC-2.10-02），续播报那个位置（幂等，等于服务端已有的值）。
2. 暂停上报在**"待定位"窗口**里也要跳过（`_resumeAfterOpen is not null` 时不报）：那一刻 `PositionSeconds` 已被 `PlayAt` 清成 0，而 `PlayQueueAt` 与"换内核迁移"都走这个窗口，报上去同样会把续播点清零。
3. **退出 App 这一刻位置可能已经不可信**（播放元素被释放 / 正在换源 / 媒体已停 → `PositionSeconds` 可能已被清成 0），所以 `ReportProgressOnExit` 只在位置 > 1 秒时才报；否则**什么都不报**，把服务端已有的记录留着 —— 报 0 等于抹掉用户的续播点。即"抓不到最新的，就保住上一次记录的"。

- 数据库侧另查一次：同一用户同一首重复上报后**仍只有一行**（覆盖不新增）、全表无重复主键。
- 单测 76 例通过（新增 4 例覆盖 204/200 两种返回与错误映射）；Windows / Android 双端编译 0 error。
- ⚠️ **客户端端到端未点验**（无法驱动界面）：需要人工走一遍「A 端播到约 30 秒暂停 → B 端开 App 看首页卡片 → 点它应从那个位置继续」。另外"退出 App 时上报"是尽力而为（进程可能在请求发完前被挂起），真正的覆盖靠暂停/切歌/心跳。

## V2.11 离线播放数据补报

> 状态：**已完成**（2026-09-26，见 §3.11.7 实施记录）。

### 3.11.1 背景

V2.7 之后用户会在没网的时候听缓存歌曲，而 `Song.PlayCount` 只在在线播放时累加 ——
离线听得越多，服务端统计越失真，直接影响 V2.12 推荐专区的数据质量。

**补报范围（已定）**：必须同时满足 ① 服务端曲库里存在（有 `songId`）② 已缓存到本地。
本地音乐（V2.6）不补报；在线播放走现有单条上报，也不属于补报。

### 3.11.2 设计方式

**本地队列**（SQLite，与 V2.6 同一个库）

```sql
CREATE TABLE PendingPlayReports (
    Id INTEGER PRIMARY KEY AUTOINCREMENT,
    ClientReportKey TEXT NOT NULL UNIQUE,  -- 客户端生成的 GUID，幂等键
    SongId INTEGER NOT NULL,
    PlayedAtUtc TEXT NOT NULL,
    PositionSeconds REAL,
    CreatedAtUtc TEXT NOT NULL
);
```

**服务端**（新增迁移 `AddPlayReports`）

```sql
-- 由迁移生成，此处为结构参考
CREATE TABLE "PlayReports" (
    "ClientReportKey" text NOT NULL UNIQUE,
    "UserId" bigint NOT NULL, "SongId" bigint NOT NULL,
    "PlayedAtUtc" timestamp with time zone NOT NULL,
    "CreatedAtUtc" timestamp with time zone NOT NULL
);
```

**接口**：`POST /api/me/playback/reports`

```json
{ "items": [ { "clientKey": "3f2a91c4-...", "songId": 123,
               "playedAtUtc": "2026-09-18T02:10:00Z", "positionSeconds": 128.5 } ] }
```

```json
{ "accepted": 12, "duplicated": 2, "unknownSongs": [456] }
```

服务端逐条 `INSERT ... ON CONFLICT ("ClientReportKey") DO NOTHING`，**插入成功才给该歌曲 `PlayCount + 1`**
（与项目里 `Categories` 种子数据的 `ON CONFLICT DO NOTHING` 同一个套路）。
`duplicated` 表示服务端已收过；`unknownSongs` 表示曲库里已不存在（被后台删除）。
客户端对这三类结果统一从本地队列删除，**不重试**（对 unknown 尤其不要无限重试）。

**触发时机**：App 启动、`Connectivity` 恢复联网、播放结束时各尝试一次；失败指数退避，连续失败留到下次启动。

### 3.11.3 开发选型

| 项 | 选型 | 理由 |
|---|---|---|
| 本地存储 | **SQLite 表，不用 JSON 文件** | JSON 追加 = 读全量→反序列化→加项→写回，量大变慢，进程被杀易留半截文件；SQLite 有事务、唯一索引幂等、`DELETE WHERE Id IN` 清理方便 |
| 幂等键 | 客户端生成的 **GUID** | 时间桶会把同一分钟内切歌重播误判重复，也可能漏判跨分钟的重复 |
| 传输格式 | JSON | 只有网络载荷用 JSON |
| 去重落库 | `ON CONFLICT DO NOTHING` | 与项目现有风格一致，无需应用层判重 |

### 3.11.4 开发思路

1. 客户端建 `PendingPlayReports` 表与 `PlayReportQueue`（入队、取批量、按结果删除）。
2. V2.7 的缓存播放路径在"播放结束"处入队（仅当 `songId` 存在）。
3. `MusicApiService` 增 `ReportPlaysAsync`，走 `Abs(...)`。
4. 服务端：`PlayReport` 实体 + `dotnet ef migrations add AddPlayReports` + `PlaybackService.AcceptReportsAsync` + 接口。
5. 补报调度：启动钩子 + 联网变化事件 + 退避重试。
6. 观察：后台或日志可看到补报量，便于核对统计是否失真。

### 3.11.6 已知问题（动手前必须先处理）

**离线待补报队列没有账号维度**（2026-09-25 记录，来自排查"退出登录后歌还在响"时顺手发现的同族问题）

现状：`PendingPlayReportStore.EnqueueAsync(songId, positionSeconds, playedAtUtc)` 只写入
`ClientReportKey`（幂等 GUID）/ `SongId` / `PlayedAtUtc` / `PositionSeconds` / `EnqueuedAtUtc`，
**没有记录这条播放属于哪个账号**。

后果：A 离线攒下一批 → 退出登录 → B 登录并联网触发补报 → 服务端按 B 的令牌写入
`PlayReports.UserId = B`，A 的离线播放整批记到 B 名下。`PlayCount` 是全局计数，
所以推荐数据（V2.12 的数据源）不受影响；受损的是 `PlayReports` 的归属正确性，
以及将来任何"我的播放历史"类功能。

**处理建议**：入队时把当时登录的 `UserId` 一并写进队列行（本地 SQLite 加一列即可），
flush 时**只提交属于当前登录账号的行**；别的账号的行留在队列里等那个账号再登录，
不删也不改归属。代价是这些行会占队列（上限 `MaxRows = 5000`，超出丢最旧的），
离线多账号交替使用属极端场景，可以接受。
⚠️ 不要用"退出登录时清空队列"来绕过：那是丢数据，丢掉的正是服务端该有的统计。

**顺带对齐**：3.11.2 里的本地表是设计初稿（复数 `PendingPlayReports`、自增 `Id`、
`PositionSeconds REAL`、`CreatedAtUtc`），而 V2.7 实际落表是单数 `PendingPlayReport`、
`ClientReportKey` 作主键、`PositionSeconds` 为 int、时间列叫 `EnqueuedAtUtc`（4.2 的迁移清单
也记了"实际表名，单数"）。实现 V2.11 时以**代码现状**为准，别再按初稿建第二张表。

### 3.12.6 后续修正：播放列表浮窗点击不稳定 + 标题间距

> 真机验收（V2.12 之后）发现两点问题，已修。

1. **浮窗内点歌要"点很多次才切换"**：队列列表行原本是 `PressFeedbackBehavior`（指针手势，负责按压动效）
   外加一个独立的 `TapGestureRecognizer`（负责点击）。在 `CollectionView` 里，Android 把几像素的指尖漂移当成小幅滚动、
   把这一次 `TapGestureRecognizer` 吞掉，表现就是"点了很多次才有一次命中"。
   **修法**：点击改走 `PressFeedbackBehavior` 自己的指针事件流（`PressedPoint` → `Released` 位移 ≤ `TapSlop=14dp` 即判为点击，
   触发新增的 `Tapped` 事件），不再挂独立 `TapGestureRecognizer`，消除"动效手势 vs 点击手势"的互相干扰。
   已去掉 `TapGestureRecognizer` 的两处（主页 / 播放页的队列浮窗）都改成 `PressFeedbackBehavior Tapped="OnQueueItemTapped"`，
   处理器签名改为 `(object?, EventArgs)`。
   **验证（真机）**：模拟 0/6/10/14/18px 漂移点击，6 次全命中 `PlayAt`；仅 24px 这类明显拖动才作为滚动处理。
2. **「播放列表」标题与列表间距过大**：标题行 `Padding` 由 `16,14` 收到 `16,8`，列表 `Margin` 由 `0,4` 收到 `0,2`
   （主页、播放页两处队列浮窗同步调整）。

### 3.12.7 V2.12 实施记录（2026-09-26 完成）

**落地范围**：后端（实体 + 迁移 + `RecommendService` + 两个控制器）+ 后台前端（推荐位管理页）+ 客户端（首页推荐专区）。

**与设计稿的两处差异（均已与需求方确认）**

1. `AdminRecommended` 在 `(PlaylistId, SortOrder, Weight)` 之外**多一列 `IsHidden`**。
   原设计写"可置顶/加权/下线"，但三列里没有能表达"下线"的字段；用 `SortOrder = -1` 之类特殊值表达
   语义隐晦、后续维护者必踩，故加显式布尔列。
   `PlaylistId` 直接做主键（一个歌单只允许一条干预记录）—— 后台重复提交是 UPDATE，不会插出第二行。
2. 接口**多一个场景 `scene=zone`（配 `categoryId=`）**。设计稿的规则表里有"分区推荐"，接口清单里却漏了，
   已确认纳入本期。缺 `categoryId` 时返回**空列表**而非静默换场景：空态用户会去查，错的数据不会。

**排序总公式**（五个场景共用，只有"场景分"不同）：

`人工置顶序号 → 规则分 + 人工加权分 → 创建时间 → Id`

- 置顶（`SortOrder > 0`）是**独立的第一个排序键**，所以能压过规则分 —— 运营置顶要的就是
  "不管播放量多少先放第一"，靠加分做不到"不管多少"。
- 加权是加分（可为负，用于压低高分但内容不好的歌单），只挪名次、不改规则本身。
- 末位用 `CreatedAt → Id` 双层兜底：没有它时 PostgreSQL 对同分行的顺序不作保证，翻页会重/漏。
- ⚠️ 实现时踩到的坑：`ThenBy` 的置顶键最初只判了 `Pin != null`，
  于是"有干预行但 `SortOrder = 0`"（只设了加权、或只设了下线）会拿到排序键 0，
  比未置顶歌单的 `int.MaxValue` 还小，被**误当成置顶**排到第一名。
  已被 `Weighted_ShiftsRankingWithoutPinning` 用例抓住并修正。两处置顶判定（推荐排序 / 后台列表表头序）必须同义。

**场景分来源**：`hot` / `zone` = 歌单内全部歌曲 `PlayCount` 之和（与 V2.4 列表同一条子查询口径）；
`collected` = 收藏人数；`new` = 无分值（靠 `CreatedAt` 兜底）；`for-you` = `3 ×`命中用户兴趣分类的歌曲数
`+ 2 ×`命中用户兴趣歌手的歌曲数 `+ 3 ×`歌单自身分区命中。兴趣来源两路合一：
喜欢的歌曲（含联合创作者）+ 收藏过的歌单分区。
`for-you` 在**未登录**、或**登录但没有任何口味信号**时退化为热播 —— 后者是冷启动，
给一份全 0 分的"个性化"榜单（等于按创建时间倒序）不如给通用榜单合理。

**顺带修掉一处历史漂移**：`PlaybackProgress.DeviceName` 的手写迁移建的是 `varchar(64)`、手写快照里也记着
`MaxLength(64)`，唯独 **`MusicDbContext` 的模型配置漏了这一句**。后果是每生成一次迁移，EF 都会按模型
（无长度 = `text`）把这一列"改回 text"并附一句"可能丢数据"的警告 —— 与当次改动无关却会混进 diff。
补上模型声明后 模型 = 快照 = 库，三者一致。

## V2.13 技术债清理：本地路径被 BaseUrl 拼接污染

> 状态：**已完成**（2026-09-26，见 §3.13.7 实施记录）。来源为 V2.6 真机验收中反复暴露的同类缺陷。
>
> ⚠️ 下表"状态"列是**本节写成时**的情况（五处逐点打补丁）。根因直到 §3.13.7 才处理掉，
> 且在这期间又漏出了第六处（亚克力底图 / 主题色取色），见该节。

### 3.13.1 背景

V2.6 引入本地音乐库后，「图片/音频地址拼接」这个动作在**五处**独立实现里各自出错，
症状都是"本地资源被拼成假 URL 后加载失败"，但表现位置不同，每次都要单独排查：

| 序 | 位置 | 症状 | 状态 |
|---|---|---|---|
| 1 | 列表封面 `AbsoluteUrlConverter` | 列表左侧封面空白 | 已修（转换器识别本地路径） |
| 2 | 播放页封面 `PlayerService.CoverUrl` | 播放页封面空白 | 已修（源头不拼接） |
| 3 | 播放页长按预览 / 保存封面 | 预览空白、保存失败 | 已修（改走 `ImageSourceFactory`） |
| 4 | 通知栏封面 `MediaNotificationManager.UpdateCoverAsync` | 通知栏显示应用图标而非专辑封面 | 已修（改走 `ImageSourceFactory.ReadBytesAsync`） |
| 5 | 系统媒体元数据 `PlayerService.MetadataArtworkUrl` | 同上（锁屏/车机等系统面板） | 已修（本地歌原样传） |
| 6 | 亚克力底图 / 主题色取色（Android+Windows 各一套，共四处） | 本地歌没有磨砂底图、主题色回默认 | **本节写成后才出现**，§3.13.7 已修 |

**当前修复方式是"逐点打补丁"**：新增 `Services/ImageSourceFactory.cs` 作为统一入口
（认得 `http` / 裸绝对路径 / `file://` / `content://` / `data:`），并让各处改走它。
但 `ApiConfig.Absolute` 本身仍然会对**裸 Unix 绝对路径**做拼接，只要将来新增一处
"取地址 → 拼 BaseUrl"的调用，同样的坑会第六次出现。

### 3.13.2 根因

`ApiConfig.Absolute` 的放行名单是**白名单前缀匹配**：

```csharp
if (url.StartsWith("http://") || url.StartsWith("https://") ||
    url.StartsWith("file:") || url.StartsWith("content:") || url.StartsWith("data:"))
    return url;
return $"{BaseUrl.TrimEnd('/')}/{url.TrimStart('/')}";
```

Android 本地曲库的封面落在 `FileSystem.AppDataDirectory`，实际形态是
**裸 Unix 绝对路径**（`/data/user/0/com.yinyan.music/files/local-covers/xxx.jpg`），
不带任何协议前缀，因此不在放行名单里 → 被拼成
`https://yinyan.oscode.top/data/user/0/...` 这种必然 404 的假地址。

> 注意：**不能简单地"以 `/` 开头就当本地路径"** —— 后端返回的封面就是
> `/media/image/xxx.jpg` 这种形态，同样以 `/` 开头。误判会让所有在线封面加载失败。
> 这也是当初写成白名单而不是"看起来像路径"的原因。

### 3.13.3 建议方案

**方案 A（推荐）：让 `ApiConfig.Absolute` 具备"文件存在性"判据**

复用 `ImageSourceFactory.IsLocalFile` 的既有逻辑（其中已包含
「以 `/` 开头 **且** `File.Exists(raw)` 为真」这一条），把 `ApiConfig.Absolute`
改为：白名单前缀 **或** 本地文件存在 → 原样返回。

- 优点：从根上堵住，所有调用点自动受益，无需逐处记得处理。
- 代价：每次拼接多一次 `File.Exists`（stat）。调用点在列表虚拟化下只对可见行触发，
  开销可接受；但**播放/进度等高频路径需确认不在此列**。

**方案 B：保留 `ApiConfig.Absolute` 语义不变，强制所有取址走 `ImageSourceFactory`**

- 优点：改动面小、语义清晰（一个负责"后端资源"，一个负责"任意图片来源"）。
- 缺点：靠约定而非类型系统保证，新代码仍可能绕过；需在文档与代码注释里反复强调。

**方案 C：引入 `MediaRef` 值类型区分"远程资源"与"本地资源"**

- 从类型层面消除歧义，但改动面覆盖 DTO、映射、播放链路，**性价比最低**，
  除非后续 V2.7（缓存）/ V2.11（补报）出现更多地址形态，否则不建议现在做。

### 3.13.4 回归清单（实施时必须覆盖）

1. **在线封面**：首页/搜索/歌单详情/歌手页/专辑页/用户头像（含 V2.5 的 `data:` URI 头像）。
2. **本地封面**：本地音乐列表、播放页、长按预览、保存封面、通知栏、锁屏媒体面板。
3. **音频地址**：在线播放（http）、本地播放（`content://` / 裸路径）、离线场景。
4. **非媒体地址**：设置页的连通性测试、后台管理端接口调用（确认未被误判为本地文件）。
5. **双端**：Windows（盘符路径）与 Android（Unix 路径）各跑一遍。

### 3.13.7 V2.13 实施记录（2026-09-26 完成）

**采用方案 A**（让 `ApiConfig.Absolute` 自带"是不是设备上的文件"判据），没有退到 B / C。

**与设计稿的差异：判据落在新建的 `Core/MediaAddress`，而不是留在 `ImageSourceFactory`**

设计稿写的是"复用 `ImageSourceFactory.IsLocalFile` 的既有逻辑"。实际做法是把这份判据**上移到 `YinYanMusic.Core`**
（新建 `MediaAddress`），`ApiConfig` 与 `ImageSourceFactory` 都改成复用它，`ImageSourceFactory` 里那份删掉。两个理由：

1. `ImageSourceFactory` 带 MAUI 依赖（要构造 `ImageSource`），单测碰不到 —— 这正是这份逻辑先前在两处各写一份、
   还各漏一种形态却一直没人发现的原因。搬到 Core 后没有平台依赖，可以直接单测。
2. 依赖方向：Core 不能反向引用 App，所以这份实现只能上移、不能下放。

`LocalPathOf` 一并上移（纯字符串处理），顺带修掉它自己的一个缺陷（见下）。

**顺带修掉的第二个缺陷：`LocalPathOf` 在 Windows 上多留一个前导斜杠**

旧实现是 `stripped.StartsWith('/') ? stripped : "/" + stripped`，只考虑了 Unix。而 Windows 的
`new Uri(path).AbsoluteUri` 产出的是 `file:///C:/x.jpg`，剥掉前缀后是 `/C:/x.jpg` 并被原样返回 ——
交给 `File.ReadAllBytes` 就是一个带盘符冒号的畸形路径，**必然取不到文件**。
新实现按"三斜杠+盘符 / 两斜杠+盘符 / 单斜杠+盘符 / 三斜杠+Unix / 畸形"几种形态分别处理，
Unix 侧行为与旧实现完全一致。

顺带一个容易踩的细节：**不能按固定位数切字符串**（`"file://"` 是 7 个字符、`"file:/"` 是 6 个），
先剥 `"file:"` 再判断剩下的是不是 `//` 开头，否则单斜杠写法会被吃掉盘符冒号。

**同一份逻辑的第三份复制：`LocalFileAccess.Normalize`**

`LocalFileAccess.Normalize` 里也有一份 `file://` 前缀剥离，带着**同样的**前导斜杠缺陷
（Windows 上 `file:///C:/x.mp3` → `/C:/x.mp3` → `File.Exists` 为 false → 本地歌被误判成"文件已失效"）。
已改为委托 `MediaAddress.LocalPathOf`。这一处是 `grep` 收尾时发现的 —— 设计稿 §3.13.6 第 5 步要求做的正是这件事，
而它当初只点名了 `ApiConfig.Absolute`。

关于判定范围的一个取舍：`IsLocalFile` 用 `"file:"` / `"content:"` **前缀**而不是 `"file://"` / `"content://"`，
与 V2.13 之前 `ApiConfig` 白名单的范围**完全一致** —— `file:/C:/x.jpg`（空 authority 的单斜杠写法）
也是合法 file URI，收窄成双斜杠会把以前能放行的形态重新变成"被拼 BaseUrl"。客户端自己只会产出双斜杠形态
（见 `LocalFileAccess`），这里放宽纯粹是为了不制造回归。

**根因修掉之后，一并删掉冗余的逐点补丁**

`PlayerService.PlayAt` 里原有一个 `song.IsLocal ? 原样传 : ApiConfig.Absolute(...)` 的分支。
`Absolute` 现在能正确处理本地路径，这个分支已无必要 —— 删掉，免得读者以为本地封面还得靠它特判。
"无封面时必须显式赋空串"那条真机 bug 的约束仍然成立（`Absolute(null / 空白)` 返回空串），注释已保留。

**第六处的修法：统一字节来源，而不是把 `Absolute` 的修法在四处各抄一遍**

四处服务（Android / Windows × 亚克力底图 / 主题色）原来的写法是「`ApiConfig.Absolute(coverUrl)`
然后要求结果以 `http` 开头」。本地封面是裸路径或 `content://`：前者被拼成 `https://域名/data/user/0/...`
（过了守卫、下载 404），后者直接被守卫挡掉 —— 两条路都静默降级成"纯遮罩 / 默认色"，不报错，所以一直没被发现。
修法是把**字节来源**统一换成 `ImageSourceFactory.ReadBytesAsync(raw, HttpClient, ct)`：
http / `data:` / `file://` / `content://` / 盘符 / 裸路径都能出字节，解码部分一行没动。
`ReadBytesAsync` 新增可选的 `HttpClient` 参数，让这四处继续复用自己的**静态**实例
（不传就会每次 new 一个，远程封面多一次 TLS 握手）。位图缓存键改用**原始地址** ——
同一张封面在"绝对 URL"与"本地路径"两种形态下语义不同，用原始串做键更省心，也不会在改服务器地址后命中旧缓存。

**性能核对（设计稿 §3.13.3 要求实施前先做的事 / TC-2.13-06）**

- 方案 A 的代价是"每次拼接多一次 `File.Exists`"。为把它压掉，`MediaAddress.IsLocalFile` 对 `/media/`
  前缀**短路返回 false**（后端媒体资源一律在这个前缀下，Scanner 写库时就是这么约定的）。因此封面 / 音频 / 歌词
  这类绝大多数地址**零额外 stat**，只有字符串前缀比较。顺带堵住一个真实风险：万一磁盘上恰好存在
  `/media/image/x.jpg` 同名路径，没有这条短路就会被误判成本地文件、所有在线封面一起挂掉（TC-2.13-03）。
- 逐条核对现有 `ApiConfig.Absolute` 调用点的调用频率：

  | 调用点 | 频率 | 影响 |
  |---|---|---|
  | `MusicApiService.Abs()` | 每次接口请求 | 参数是 `api/...`，不以 `/` 开头 → 不 stat |
  | `ImageSourceFactory.From` / `ReadBytesAsync` | 列表虚拟化下每可见图一次 | 本地封面在 `From` 里已提前返回，**不会**再进 `Absolute` |
  | `PlayerService.PlayAt` | 每次切歌 | 封面 + 音频各一次，均为前缀判定 |
  | 亚克力底图 / 主题色四处 | 每次切歌（有位图缓存） | 已不再走 `Absolute` |
  | `PlaylistDetailViewModel` / `AccountEditViewModel` / `CacheDownloadService` / `ApiConfigStore` | 页面加载 / 保存 / 连通性测试 | 低频 |

- **进度条刷新路径确认不受影响**：`PlayerService` 的 500ms 定时器（`Device.StartTimer`）只读
  `_player.Position` / `Duration` 并赋给秒数，**不解析任何地址**，所以"高频路径引入 stat 抖动"这个风险
  在本版实现里根本不存在。
- 结论：**不需要退回方案 B**。

**测试**：新增 `MediaAddressTests` 35 例，全套 **154 例全绿**（原 119 例）。覆盖到的用例：

- **TC-2.13-03**：`/media/...` 同名假路径永不判成本地（含 `/api/media/...` 变体）。
- **TC-2.13-04**：本地文件不存在的两半 —— 仍判成本地、不拼 BaseUrl（判据不看存在性）；
  读取失败由 `ReadBytesAsync` 的 try/catch 兜底成 null（MAUI 侧，靠真机回归）。
- **TC-2.13-05**：Windows 盘符判定，外加一条**真实 `Uri` 往返** —— `new Uri(真实文件)` → `LocalPathOf`
  → 仍能 `File.Exists` 到，并断言结果**不带**前导斜杠（旧实现在这里必然失败）。
- `LocalPathOf` 的十种写法（含单斜杠 `file:/C:/...`、畸形写法）逐个锁死。
  因为 `LocalFileAccess.Normalize` 现在委托同一实现，这一组用例同时覆盖了它。

这部分能自动化，正是因为判据搬到了无平台依赖的 Core。TC-2.13-01/02/06/07 涉及真实 UI 与设备，仍按 §3.13.4 走真机回归。

**待用户验收（本 agent 无法验的部分）**

- 真机：本地歌在播放页 / 队列浮窗的**亚克力底图与主题色**现在应当能取到（第六处修复的直接效果）；
  同时确认在线封面、`data:` 头像不回归（TC-2.13-01）。
- `LocalFileAccess.Normalize` 的收口影响**本地歌的"文件是否仍可访问"判定**（本地音乐页、失效提示分支）。
  Windows 上路径形态是盘符路径，`Normalize` 对它的行为没变；受影响的只是"库里存了 `file://` 形态"这种情形，

## V2.14 技术债：歌曲时长与音频实际不符

> 状态：**已完成**（2026-09-26，见 §3.14.6 实施记录与遗留项）。来源为 V2.7 真机验收（2026-09-22）时日志里反复出现的告警。
> 用户已确认：**先记进文档，暂不动工**。

### 3.14.1 现象

V2.7 真机验收时 logcat 持续出现：

```
YinYan: 时长偏差: API=189s, 实际=234s, 歌曲=向日葵
YinYan: 时长偏差: API=212s, 实际=190s, 歌曲=closer
YinYan: 时长偏差: API=237s, 实际=227s, 歌曲=逆光
```

`PlayerService.OnMediaOpened` / `OnStateChanged` 里现有的守卫是：

- API 时长 > 0 且与实际偏差 > 5s → **只打日志，不回填**（保留 API 的权威值）；
- 仅当 API 时长 ≤ 0（服务端没解析出来）才用实际时长回填 `DurationSeconds`。

由此推出的**当前实际行为**（这几条都还没专门验证，实施前需先确认）：

1. 列表与播放页展示的时长来自 API，因此是错的；
2. 播放开始后 `DurationSeconds` 仍是 API 值 → **进度条总长与实际音频长度不符**：实际更长时进度会顶到甚至越过末端，实际更短时进度条走不满；
3. 通知栏与系统媒体面板的总时长同样取自 `DurationSeconds`，一并错；
4. V2.10 的播放进度同步若按绝对秒记录，跨端续播的位置会偏；V2.4 的统计口径不受影响（它统计的是次数）。

### 3.14.2 根因（**待核实**，勿照此直接改代码）

候选方向，实施前必须先做一次全量对账摸清偏差分布（多少首、偏多少、集中在哪批导入的文件）：

1. 服务端 Scanner 入库时用 TagLib 解析出的时长与文件实际不符 —— 需核实它的取值字段与算法，以及是否和客户端 `LocalMetadataReader` 同一口径（向下取整/精度）；
2. 音频文件在入库后被替换或重新压制，但库里的元数据没跟着更新；
3. 个别有损文件（VBR）头信息本身不准。

### 3.14.3 建议方案（按性价比排序）

**方案 A（改动最小，治标）**：客户端播放时若偏差 > 5s，用实际时长覆盖本地展示与 `DurationSeconds`，不动服务端数据。
缺点：两端仍不一致（列表是 API 值、播放页是实际值），且下次请求刷新列表又会变回去。

**方案 B（推荐，治本）**：服务端增加"时长对账"任务，可挂到 V2.8 的目录扫描定时器上：
对偏差超过阈值的歌重新解析音频并把 `Songs.DurationSeconds` 回写；后台给一个"时长异常"列表入口（数量 + 可手动触发重扫）。

### 3.14.6 实施记录与遗留项（2026-09-26）

> 本节的处置方式与其它版本不同：**没有写新代码**，而是回头核对了"这个债是否还在"。
> 结论是根因与存量数据都已解决，但设计稿 §3.14.3 建议的三件事只做了一件半 —— 逐条列在下面。

**已解决的部分**

1. **根因候选 #1（解析口径分叉）已消除**。时长解析统一走 `Mp3DurationReader`（ATL 逐帧解析）+ 全项目向下取整；
   早期"TagLib 估算时长 + `Math.Round`"分叉出的 1 秒偏差已不存在。这一修复是在 V2.8 的第二 / 第三轮验收里
   顺带完成的（见 §3.8.7 表格第 2 行），本版只是确认它覆盖了 §3.14.2 点名的第一个候选方向。
2. **存量数据已清理（本次实测）**。对本地库做了只读对账：456 首逐首比对「`Songs.DurationSeconds`」与
   「ATL 实测时长」→ **456 一致 / 0 不一致 / 0 首解析失败**。同时也说明：§3.14.1 里点名的那三条告警
   （向日葵 API=189s、closer API=212s、逆光 API=237s）现在库值都与文件实测吻合，
   其中《向日葵》已从 189 变成 259（ATL=259.656，文件自 2026-03-09 未变）—— 是被重算工具改对的。
3. **全量重算工具已就位**。`AdminService.ScanDurationsAsync`（逐首重解析并回写，只在**确实变化**时计数与写库）
   经 `POST /api/admin/scan-durations` 暴露，挂在 `IScanGate` 之后（并发时 409），后台「系统任务 → 扫描时长」有按钮。
   即 §3.14.3 **方案 B 的手动重扫部分**。
4. **方案 C 的精神已满足**：扫描入库时解析不出时长的文件直接拒绝入库，不会继续产生脏数据。

**明确未做的部分（本版不做，记录在此）**

1. **方案 B 的"自动对账"没做**：定时扫描（`DirectoryScanService`）对**已存在**歌曲只在 `DurationSeconds <= 0` 时补时长，
   不纠正"有值但偏"的。也就是说，将来若某个音频文件被替换而元数据没跟着更新，得**人工去点一次「扫描时长」**才会修正。
   要做的话建议挂到 V2.8 的定时器上、加一个偏差阈值。
2. **方案 B 的"时长异常列表入口"没做**：后台只有"手动重扫"按钮，没有"有多少首偏差、偏差多少、都是哪几首"的列表。
   本次对账是靠一次性脚本临时算的，没有沉淀成常驻能力。
3. **客户端仍以 API 时长为权威**（§3.14.1 列的"当前实际行为"四条依然成立）：`PlayerService` 的
   `OnMediaOpened` / `OnStateChanged` 对偏差 >5s 只打日志不回填，仅当 API 时长 `<= 0` 才用实际时长回填。
   即 §3.14.3 **方案 A 没做**。当前库值已全部正确，所以这条暂时不产生可见问题；
   但若再出现"库值偏"的情况，进度条总长仍会与实际不符。

**遗留的一条无法定论项**：`closer` 与 `逆光` 的库值 / ATL 值彼此吻合（212 / 237），
而 §3.14.1 里客户端媒体引擎当时读到的是 190 / 227。也就是说这两条的残差**不在服务端数据上**，
而在客户端引擎读数上。要定性得在真机上复现，本次未做。

## V2.15 后台系统消息推送

> 状态：**已完成（含遗留项）**。后台管理员可通过后台系统向全部用户 / 部分用户 / 单个用户推送通知，
> 用户在 App 内实时接收消息与通知（未读角标 + 通知列表）。实施记录与遗留项见 §3.15.7。

### 3.15.1 背景与目标

当前系统没有任何站内信 / 通知能力：管理员要触达用户只能靠"改库"或发外部消息。
本迭代补齐**站内通知**闭环：后台发起 → 服务端落库并实时推送 → App 实时收到并可标记已读。

### 3.15.2 功能范围

**后台（`web/admin`）**

- 新增「消息推送」管理页：
  - 新建通知：标题、正文、可选关联对象（歌曲 / 歌单 / 专辑，点击跳转，**三选一**）；
  - 接收范围：**全部用户** / **部分用户**（按用户 ID 列表，可复用现有用户管理页选择）/ **单个用户**；
  - 发送后进入「已发送」列表：发送时间、目标范围、接收人数、状态（发送中 / 已完成 / 失败）。
- 复用 V2.3 的后台布局与权限（`[Authorize(Roles="admin")]`）。

**服务端 API**

- 新表：
  - `Notifications`：通知本身（标题 / 正文 / 目标范围 / 关联对象 / 发送状态 / 发送人 / 时间）；
  - `NotificationRecipients`：通知 × 用户的接收与已读状态（`(NotificationId, UserId)` 唯一）。
- 新接口（均需登录 JWT）：
  - `GET /api/notifications`：分页拉取自己的通知（未读在前）；
  - `GET /api/notifications/unread-count`：未读数（角标轮询/初始值）；
  - `POST /api/notifications/{id}/read`：标记单条已读；
  - `POST /api/notifications/read-all`：全部已读；
  - `SignalR Hub /hubs/notifications`：实时推送新通知与未读数变化。
- 管理接口：
  - `POST /api/admin/notifications`：发送通知（范围：全部 / 部分 / 单个）；
  - `GET /api/admin/notifications`：已发送列表。

**客户端 App**

- 「我的」页新增「消息通知」入口（未读红点/数字角标）。
- 通知列表页：标题 / 正文 / 时间 / 已读状态，支持单条已读与全部已读；点击带关联对象的通知跳转
  （歌曲 → 播放页；歌单 → 歌单详情页；专辑 → 直接播放整张专辑，「点专辑=播放整张」是本 App 既有语义，
  专辑没有详情页）。
- **实时接收**：SignalR 长连接（登录后建立，断线自动重连）；收到新通知时：
  - 应用内 Toast 提示 + 未读角标 +1；
  - 可选增强（不在本期默认范围）：Android 通知栏本地通知。
- 客户端本地 SQLite 缓存最近 N 条通知，离线也能看到历史（可选，V2.15 初版可先不做）。

### 3.15.3 技术方案

- **实时通道选型：ASP.NET Core SignalR**。理由：服务端已是 ASP.NET Core 自托管，
  无需引入 Firebase / 第三方推送；Android 与 Windows 客户端均可用 `Microsoft.AspNetCore.SignalR.Client`，
  符合官方推荐的实时方案。长轮询作为降级（SignalR 自动支持）。
- 认证：Hub 连接通过 `?access_token=<JWT>` 校验（SignalR 标准做法），与 Web API 同一套 JWT。
- 全部用户推送：发送时按当前用户列表批量生成 `NotificationRecipients`；
  用户量大时改为"读取时物化"（先记通知，用户拉取/推送时再建接收记录）——初版先批量生成，量级上来再优化。
- 未读数：`NotificationRecipients` 按 `UserId + IsRead=false` 计数，SignalR 广播 `UnreadCountChanged`。

**本版踩坑记录（都是沉默失效、不报错的那类）**

1. **`CollectionView` 不算条目模板根元素的 `Margin`**。通知卡片最初写
   `Margin="13,7,13,7"`，实测完全没生效：截图纵向扫描显示四张卡片的背景色连成
   376px 一片、缝隙为 0（横向也只到页面 `Padding` 的 16，而不是 16+13）。
   改法：卡片间距交给容器 —— `VerticalStackLayout Spacing="18"` + 卡片 `Margin="13,0,13,0"`
   （「我的」页的写法）；条目根元素用 `Grid` + `Padding` 也是可靠的。
   代价：`BindableLayout` 没有 `EmptyView` 与虚拟化，空态要自己在 VM 里判。
2. **MaterialIcons 的图标字形不能直写进 `Text`**。写私有区字符（U+E5xx）时经一次
   编码往返被写坏成 `顥?`（U+9865 U+003F），表现为箭头整块不渲染且**不报任何错**。
   一律用 XML 实体（`&#xE5C4;` / `&#xE5CC;`）。
3. **标题居中不能用 `ColumnDefinitions="40,*,Auto"`**。右侧是文字按钮（比 40 宽）时
   标题会被挤偏；且该按钮在"无未读"时会隐藏，标题跟着左右跳。
   标题要单独占一层、按整条宽度居中，按钮叠在其上左右贴边。
4. **后台请求偶发连接级失败**：本环境 Kestrel 复用连接时约 1/4 请求被重置
   （前端 `http.ts` 的 `RETRYABLE_CODES` 与 `vite.config.ts` 注释记的是同一现象）。
   端到端脚本与前端都为幂等请求加了重试；写新脚本时不要假设一次就能成。

**遗留项（待用户验收）**

1. **真机双端回归未做**（TC-2.15-01~09，尤其 TC-2.15-08 断线重连、TC-2.15-09 双端一致）——
   需要两台真实客户端 + 运行中的 API 才能验。
2. **Android 通知栏本地通知**未做（设计里就标注为"不在本期默认范围"）。
3. **客户端本地 SQLite 通知缓存**未做（设计标注"初版可先不做"）：
   离线时只能看到上次联网拉到的列表，无法看离线期间的历史。
4. **全部用户推送是发送时物化接收行**：用户量上来后大群发的写放大明显，
   设计 3.15.3 提到的"读取时物化"留待后续优化。
5. **后台「选择用户」是远程搜索下拉**，不是设计里提的"复用用户管理页选择"；
   大批量勾选体验弱于专门的选人弹窗。

**封面另存改存公共 Download（2026-09-28）**

需求：封面另存在手机上落进了应用私有目录（`Environment.SpecialFolder.MyPictures` 在 Android 解析到内部存储，文件管理器根本看不到 —— 用户报"Android/data 里也找不到"）。改为与网易云"下载"同一套公共目录机制：

| 端 | 落点 | 权限 |
|---|---|---|
| Android 10+ | 公共 `Download/YinYanMusic/`（`MediaStore.Downloads` 插入；重名系统自动加 " (n)"，展示名回读后进成功提示） | **无需任何存储权限**（向共享空间贡献自己的文件） |
| Android 7~9 | 公共 `Download/YinYanMusic/` 直写（重名手动加 " (n)"） | 运行时 `WRITE_EXTERNAL_STORAGE`（manifest 仅 maxSdk=28 声明），复用 `AndroidLocalMediaScanner` 的权限桥接器（RequestCode 1002） |
| Windows | 维持"图片"库下的 YinYanMusic（本就资源管理器可见，对图片也更合惯例） | — |

实现要点：新增 `Services/CoverSaveService.cs`（`#if ANDROID / #elif WINDOWS` 成对，全局约束 4）；`NowPlayingPage.OnSaveCoverClicked` 只负责读字节、按文件头判扩展名、组文件名（规则不变：`歌名-全部歌手`、`_` 连接），落盘全部交给服务；MediaStore 写流失败时删掉半截文件不留脏数据。媒体库列名直接用字面量（`_display_name` 等），不绑定各 API 版本的 MediaColumns/IMediaColumns 形态差异。编译：Android / Windows 双目标 0 error；**真机保存后到文件管理器 Download/YinYanMusic 查看待验收**。

### 4.4 风险登记

| 风险 | 影响 | 处置 |
|---|---|---|
| **P0 基线缝合判断错** | 老库被当成新库 → 建表失败；或新库被当成老库 → 结构缺失 | 三态判据同时检查核心表与历史表；上线前在备份库验证（TC-P0-02/03） |
| **P0 迁移后结构漂移** | 某环境手工改过库，导致后续迁移失败 | 上线后核对各环境 `GetPendingMigrations()`；禁止手工改库 |
| P0 未备份就升级生产 | 迁移失败无法回退 | 生产升级前必须备份；保留 `DROP_DB=1` 供开发环境重建 |
| **P1 文档暴露到公网** | 完整接口清单与调试入口外泄 | 生产默认关闭；开放时 Nginx 侧限制（IP 白名单 / Basic Auth），TC-P1-08 必测 |
| P1 Scalar 资源依赖 CDN | 内网/无外网部署时 UI 打开是空白页 | TC-P1-11 验证；必要时改自托管静态资源 |
| 客户端首次引入 SQLite | V2.6 是全新地基，Android/Windows 路径与打包需验证 | V2.6 只做最小可用（扫 + 播），不铺开 UI |
| Android 存储权限被拒 | 扫描能力不可用 | 明确引导 + 提供手动选目录兜底 |
| 补报重复计数 | 污染统计与推荐 | 客户端 GUID 幂等键 + 服务端 `ON CONFLICT DO NOTHING` |
| 达到缓存上限 | 用户无法继续缓存 | 明确提示清理或调高上限；**不自动删除** |
| 定时任务与手动导入并发 | 重复入库 | 依赖导入按 `AudioUrl` 去重；单实例保护 |
| 评论量增长 | 列表性能、审核压力 | 先做分页 + 后台隐藏，暂不上敏感词与反垃圾 |
| 推荐规则效果不达预期 | 专区点击率低 | v1 保留人工加权兜底，数据积累后再评估算法 |
