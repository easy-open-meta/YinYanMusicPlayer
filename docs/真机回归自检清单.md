# 真机回归自检清单（交付前必过）

> 立这份清单的原因：2026-09-22 一天之内因为"改完就交付、没回验"出了**三次回归**
> （① 图标全变方框 ② 播放有进度没声音 ③ 点在线歌播不了），还把一次 `exit=1` 的失败构建当成成功。
> **从此：凡改动触及下列任一区域，交付前必须按清单逐条验证，并把"硬证据"（日志/截图）贴给用户。**
>
> 判据一律用**可观测事实**（logcat 行、AudioTrack 振幅、通知栏截图），不许用"应该没问题""编译通过"。

## 0. 构建完成的判据（先看这个）

- [ ] **只认日志里的 `dotnet_exit=0`**（后台任务的 "exit code 0" 是 PowerShell 的，不是 `dotnet build` 的）
- [ ] `error CS / APT / XA / MSB` 计数为 0
- [ ] **扫一遍 APK 资产**：`tar -tf <apk> | findstr ttf` 必须含 `assets/MaterialIcons-Regular.ttf`（+ OpenSans）
      —— 缺字体 = "能装能跑但图标全是方框"的静默坏包
- [ ] Debug 包确认 DLL 已同步：设备 `files/.__override__/arm64-v8a/<App>.dll` 与本地 `bin/Debug/net10.0-android/<App>.dll` **大小一致**
      （APK 的 `lastUpdateTime` 不变是 fast deployment 的正常现象，别拿它当判据）

⚠️ **动过 `Platforms/Android/*.cs`（`#if ANDROID` 代码）必须编 Android 目标** —— Windows 目标根本不编译这些文件，会全绿放行。

## 1. 播放（最高频回归区）

每次动到 `PlayerService` / 任何带 `MediaElement` 的页面 / `MediaNotificationManager` 都要跑：

- [ ] **点在线歌能播**：`PlayAt: RepeatMode=…` 正常执行，**不得出现 `PlayAt: _player 为空`**
- [ ] **真的在出声**（不用耳朵）：`AudioTrack: start` + `AUDIO_DEVICE_OUT_SPEAKER`
      + `AudioTrackImpl: [audioTrackData][fine] … maxAmplitude <非零>`
- [ ] 进度推进：`MediaSessionService … position=<增长>`
- [ ] **进出二级页面后仍可播**（本地音乐 / 缓存管理 / 播放页各进一次再返回，然后点歌）
      —— 这是"页面抢走播放内核"类回归的必经路径
- [ ] **在线 → 本地切歌，通知栏封面刷新**（切到没有封面的本地歌时应变成无封面，而不是残留上一首的封面）
- [ ] 迷你播放条与通知栏的播放/暂停/上下一曲按钮可用
- [ ] **「继续播放」卡片的设备条件**：本机自己听到一半后重进首页 → **不弹**（进度里的设备名 == 本机名）；
      换另一台设备（或库里那份进度的设备名与当前机不同）→ 才弹；设备名为空的老记录 → 也弹
      （判断不了就不假定同机，否则入口会被永久藏掉）

## 2. 缓存（V2.7）

动到 `CacheStore` / `CacheDownloadService` / 缓存管理页时要跑：

- [ ] 三个标签页都能切，计数正确（缓存中 / 缓存完成 N / 缓存历史 N）
- [ ] 手动「缓存到本地」：底部浮层出现（歌名 + 进度条 + 百分比），完成后变「已缓存 ✓」再淡出
- [ ] 通知栏出现缓存进度：`[CacheNotify] notify N 首 xx%`，下载完 `[CacheNotify] cancel`
- [ ] 「缓存中」标签页与通知栏显示**同源进度**（都来自 `ActiveDownloads`）
- [ ] 撞上限：静默跳过 + 缓存页提示"有 N 首因超过上限没有自动缓存" + 历史里出现「超上限跳过」
- [ ] **绝不自动删旧缓存**（清空只能由用户操作）
- [ ] 完整听完一首在线歌 → 自动缓存（仅 WiFi；非 WiFi 时日志应有 `当前不是 WiFi，跳过`）

## 3. 网络 / 后端

- [ ] 主机探测要 **绕过系统代理**：`curl.exe --noproxy "*" …`（否则 localhost 会返回假的 `502`）
- [ ] **四条路径**都验：主机 `127.0.0.1` / 主机局域网 IP / 真机 `adb reverse` 的 `127.0.0.1` / 真机局域网 IP
- [ ] 设备侧 `curl` 通 ≠ App 通（curl 是 native，不检查 Android 明文策略）——
      App 连不上时优先怀疑 `networkSecurityConfig`，设置页「测试连接」有双栈对照
- [ ] 明修策略机制：Debug 用 `network_security_config_debug`（明文全开），Release 用严格版；
      **明文许可只认 nsc，manifest 的 `usesCleartextTraffic` 会被忽略，`<debug-overrides>` 里放 `base-config` 无效**

## 3.5 站内通知实时通道（V2.15）

动到 `NotificationRealtimeService` / 通知列表页 / `NotificationsHub` / `AuthService` 的连断逻辑时必跑：

- [ ] 登录后 `adb logcat` 能看到 SignalR 连上（无 401）；**未登录时不得建连**
- [ ] 后台「消息推送」发一条「全部用户」→ App **实时**弹 Toast + 「我的」页角标 +1（不用手动刷新）
- [ ] 三种范围各自只到目标用户：`部分` 选两人 → 只有那两人角标变；`单个` 选一人 → 只有那人变
- [ ] 点通知 → 先变已读、角标 -1，再跳转（带歌单的进歌单页，带歌曲的进播放页，
      带专辑的**直接播放整张专辑**并进播放页）
- [ ] 「全部已读」→ 角标归零；重进页面不会又冒出来
- [ ] **断线重连**：开飞行模式 → 后台发一条 → 关飞行模式 → 角标应补上（重连后拉 `GetUnreadCount`）；
      离线期间的列表项靠页面重进时 REST 补齐
- [ ] **登出后不得再收推送**：退出登录再发一条，角标不应变化（连接已断）
- [ ] 双端（Windows + Android）各收一条，行为一致

## 4. 常驻服务（API）
- [ ] 由 WorkBuddy 会话启动的进程**都不长命**（后台任务托管、`Start-Process`、WMI 建进程皆然）
      —— 要让 API 常驻，必须用户自己在终端跑（或双击 `start-api.cmd`、`--environment Development --urls http://0.0.0.0:<port>`）
- [ ] 交付时如"当前能连"是靠我起的实例，必须明确告诉用户它有可能随会话结束消失
